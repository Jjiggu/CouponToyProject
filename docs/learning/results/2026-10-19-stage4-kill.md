# 4단계 실제 프로세스 종료 원본 (2026-10-19)

실행 조건
- 앱·DB·Redis 는 [k6 원본](2026-10-19-stage4-k6.md) 과 같다. 작업 스레드 4, 큐 50000(기본값)
- k6 `METHOD=REDIS_ASYNC SCENARIO=burst TOTAL_COUNT=1000 MEMBERS=1000 VUS=100 ITERATIONS=1000 WARMUP=0` 을 띄우고, 결과 API 를 10ms 간격으로 보다가 접수(ACCEPTED)가 300건을 넘으면 앱 JVM(18080 을 듣는 프로세스)에 신호를 보냈다. 조회와 신호 사이에도 접수가 이어져, 신호가 닿았을 때는 1000건이 모두 접수돼 있었다(클라이언트가 받은 202 = 1000)
- `kill -KILL`: 즉시 종료. `kill -TERM`: Spring Boot 정상 종료(graceful shutdown)
- 종료 뒤 MySQL(`coupon_issues` 행, `issued_count`)과 Redis(`SCARD`)를 직접 셌다. 그 뒤 앱을 다시 띄워 결과 API 의 `redisOnlyMembers` 를 보고, Redis 에만 있는 회원 한 명으로 다시 요청했다(`REDIS_ASYNC`). 진입점 요청 기록은 메모리에 있으므로 재시작 뒤 결과 API 의 `requests`·`pending` 은 비어 있다
- 실행 스크립트: `build/lab-tmp/exp4-kill.sh` (저장소 밖, 커밋하지 않음)
- "신호 직전 결과 API" 의 접수·미완료·확정은 한 응답 안에서도 읽는 시점이 조금씩 다르다(확정 → 미완료 → DB 조회 → 접수 순서). 접수가 몰리는 중에는 접수 값이 나머지보다 크게 잡힌다
