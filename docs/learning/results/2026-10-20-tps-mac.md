# 쿠폰 1장 따라간 최대 속도 측정 원본 (2026-10-20, Mac): 50 단위 일정 속도 30초

실행 조건
- 부하 테스트([2026-10-20-load-test.md](2026-10-20-load-test.md))와 같은 jar·DB·Redis·k6 설정. Hikari 4 설정은 뺐다
- 속도: 비관적 락 300·350·400·450, 나머지 450~700 (50 단위). 각 30초, 설정마다 앱을 새로 띄우고 실험 데이터를 비운 뒤 낮은 속도부터. 6개 → 5개 설정을 2회
- 앱을 띄운 직후 초당 200건 30초를 먼저 보내고 버렸다(예열). 예열 없이 시작한 첫 시도에서 첫 속도만 낮게 나왔기 때문이다: 비관적 락 300 → 287 TPS(p95 2.1초), 바로 다음 350 → 347 TPS / 동기 Lua 450 → 394 TPS, 다음 500 → 501 TPS. 원인(JIT, Tomcat 스레드 생성 등)은 나누어 확인하지 않았다
- 추가 기록: 1초마다 측정 쿠폰의 `issued_count` 와 MySQL `Com_commit`(`docker exec` 로 조회). "정상 구간 발급 TPS" = 측정 시작 5~28초 사이 `issued_count` 증가 / 23초. 괄호는 1초 구간 최소~최대
- 수정 (같은 날 EC2 측정 중 발견): 처음 요약은 정상 구간을 5~30초로 잡았다. 30초는 보내기가 끝나는 시점이라 1초 표본 사이를 직선으로 보간하면 발급이 멈춘 뒤 값과 섞여 약 1% 낮게 나왔다(보낸 요청을 모두 30.0초 안에 발급했는데도 98% 로 계산됨). 기록된 표본은 그대로 두고 5~28초로 다시 계산한 표다
- 따라간 최대 속도 조건(두 회차 모두): 정상 구간 발급 TPS ≥ 목표의 99%, k6 가 못 보낸 요청 0, 보내기 끝났을 때 미완료 ≤ 보낸 요청의 1%, 동기 방식은 HTTP p95 ≤ 500ms
- 측정 중 Mac 상태: 두 번째 시도는 다른 Java 앱(8080)이 돌던 중이라 버렸다. 그 앱을 끈 뒤 처음부터 다시 쟀고 아래가 그 결과다. 이때도 `fseventsd` 가 CPU 약 100%(측정을 멈춘 상태에서도), 스왑 약 10GB, 부하 평균 7~9 였다
- 실행 스크립트: `build/lab-tmp/exp8-tps.sh`, 요약 `build/lab-tmp/tps_report.py` (저장소 밖)
