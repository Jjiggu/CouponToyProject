# 2단계 k6 HTTP 실행 원본 (2026-10-17)

실행 조건 (1단계 k6 와 같은 조건)
- 앱: macOS 호스트에서 `./gradlew bootRun` (OpenJDK 17.0.19, 8 cores, CPU 제한 없음), 포트 18080, 프로필 local, SQL 로그 끔
- DB: 별도 스키마 `CouponToyProject_lab` (MySQL 8.0.36 Docker 1 CPU / 1GB, REPEATABLE READ 기본), Redis db 2
- Tomcat 스레드 기본 200, Hikari 최대 풀 기본 10, 낙관적 락 재시도 기본값(최대 5회, 지연 상한 100ms)
- k6 공통: `MEMBERS=1000 VUS=100 ITERATIONS=1000 WARMUP=200` (워밍업은 별도 쿠폰에 같은 방식으로 200건 순차 전송)
- 실행 순서: e1 PESSIMISTIC → OPTIMISTIC → OPTIMISTIC_RETRY → SERIALIZABLE, e2 SERIALIZABLE → OPTIMISTIC_RETRY → OPTIMISTIC → PESSIMISTIC, e3 PESSIMISTIC → OPTIMISTIC → OPTIMISTIC_RETRY → SERIALIZABLE (한 번씩). SERIALIZABLE 은 같은 세션 기준선
- OPTIMISTIC_RETRY 3건은 k6 기준값 `coupon_issue_http_duration p(95)<500` 을 넘어 종료 코드 99 로 끝났다(측정은 정상 완료)
- HTTP 응답 시간은 k6 `coupon_issue_http_duration`(발급 요청만), 서버 시간은 결과 API `latencyMs`(진입 → 반환, 재시도·커밋 포함)
- 처리량 = 결과 API 요청 수 / (setup 종료 → teardown 시작) 시간. 접수 처리량은 응답을 돌려준 모든 요청, 발급 완료 처리량은 SUCCESS 만
