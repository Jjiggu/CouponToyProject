# 2단계 보완: 락 부여 순서(CATS) 실행 원본 (2026-10-17)

MySQL 8.0.20 부터 InnoDB 는 락 대기자를 CATS(Contention-Aware Transaction Scheduling) 로만 고른다.
대기자 중 더 많은 트랜잭션을 막고 있는 쪽의 가중치가 크고, 가중치가 같으면 오래 기다린 쪽이 먼저다.
가중치는 `information_schema.INNODB_TRX.TRX_SCHEDULE_WEIGHT` 로 보이고 `LOCK WAIT` 상태에서만 값이 있다.
([MySQL 8.0 Reference Manual: InnoDB Transaction Scheduling](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-scheduling.html))

## 1. 순서 고정 재현 (JUnit)

`./gradlew test --tests '*OptimisticPessimisticLockTest.catsGrantsCouponLockByWeight'` 의 기록. 조건은 2단계 JUnit 원본과 같다(MySQL 8.0.36, RR, Hikari 10).
1. 별도 커넥션이 쿠폰 행을 `FOR UPDATE` 로 잡는다.
2. 먼저 온 요청(비관적 락)이 쿠폰 행을 기다린다.
3. 늦게 온 요청이 같은 트랜잭션 안에서 회원 행을 `FOR UPDATE` 로 잠근 뒤, 비관적 락 발급으로 쿠폰 행을 기다린다.
4. 그 회원 행을 기다리는 트랜잭션을 N 개 붙인다.
5. 가중치가 갱신된 것을 확인한 뒤 쿠폰 행을 놓는다. 재고는 1장이다.

단독 실행 4번, 전체 테스트 5번 연속으로 매번 같은 결과가 나왔다. 아래는 마지막 전체 테스트의 기록이다.

측정 결함과 수정: 처음에는 먼저 온 요청을 `innodb_trx` 의 첫 쿠폰 행 대기자로 식별했다. 그런데 전체 테스트에서 가끔 실패했다(3번 중 1번).
`innodb_trx` 는 0.1초 캐시라서, 직전 케이스가 끝나고 0.1초 안에 조회하면 직전 케이스의 대기 행이 보였다.
풀에서 재사용된 커넥션 id 까지 겹쳐 먼저 온 요청을 잘못 짚었다. 실패 시점의 가중치 자체는 정상이었다(회원 행을 쥔 늦게 온 요청 4, 먼저 온 요청 1).
대기 여부는 캐시가 없는 `performance_schema.data_lock_waits` 로 보고, 늦게 온 요청은 "회원 행 락을 쥔 트랜잭션"으로 식별하도록 고쳤다.

### CATS: 늦게 온 요청이 쥔 회원 행을 기다리는 트랜잭션 0개, 재고 1

- 쿠폰 행 가중치: 먼저 온 요청 1, 늦게 온 요청 1 (trx 817892 / 817893, 늦게 온 요청 = 회원 행 락 소유자)
- 결과: 먼저 온 요청 SUCCESS, 늦게 온 요청 SOLD_OUT
- 쿠폰 행 잠금 해제 직전 락 대기:
  - {trx_id=817893, isolation=REPEATABLE READ, weight=1, lock_mode=X,REC_NOT_GAP, locked_table=coupons, locked_index=PRIMARY, waiting_query=select c1_0.coupon_id,c1_0.cre ... e c1_0.coupon_id=56 for update}
  - {trx_id=817892, isolation=REPEATABLE READ, weight=1, lock_mode=X,REC_NOT_GAP, locked_table=coupons, locked_index=PRIMARY, waiting_query=select c1_0.coupon_id,c1_0.cre ... e c1_0.coupon_id=56 for update}

### CATS: 늦게 온 요청이 쥔 회원 행을 기다리는 트랜잭션 3개, 재고 1

## 2. 현재 흐름의 가중치 (HTTP 부하 중 표본 조사)

2단계 k6 와 같은 조건(회원 1000, VU 100, 요청 1000, 워밍업 200, Hikari 10, 별도 DB, Redis db 2)으로 실행하면서,
0.2초마다 `SELECT trx_schedule_weight, trx_query FROM information_schema.innodb_trx WHERE trx_state = 'LOCK WAIT'` 를 조회했다.
표본 간격이 0.2초라 모든 대기를 본 것은 아니다.

| 실험 | 방식 | 표본 수 | 한 표본에서 본 최대 대기 트랜잭션 수 | 관찰한 (가중치: 대기 위치) |
|---|---|---:|---:|---|
| 재고 100 | PESSIMISTIC | 21 | 9 | 1:coupon_for_update 66건 |
| 재고 1000 | PESSIMISTIC | 25 | 9 | 1:coupon_for_update 135건 |
| 회원 100×10 | PESSIMISTIC | 17 | 8 | 1:coupon_for_update 68건 |
| 회원 100×10 | OPTIMISTIC | 15 | 4 | 1:coupon_update 10건 |
