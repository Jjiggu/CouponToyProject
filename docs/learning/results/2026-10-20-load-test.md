# 부하 테스트 실행 원본 (2026-10-20): 일정 속도로 30초

실행 조건
- 같은 jar 로 발행자 `local`(18080)을 띄웠다. Pub/Sub·Stream 은 구독자·소비자 프로세스(18081)를 하나 더 띄웠다. 모두 `CouponToyProject_lab`, Redis db 2, Hikari 최대 10(동기 Lua 비교 설정만 4), 작업 스레드 4, Stream 소비자 4, SQL 로그 끔
- MySQL 8.0.36 (Docker 1 CPU / 1GB, `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`), Redis 7.2.13 (Docker 1 CPU / 1GB, AOF·RDB 끔), k6 v2.1.0. 앱, k6, Docker 모두 macOS 호스트 한 대(8 cores)
- k6 `SCENARIO=smoke`(constant-arrival-rate) `RATE` = 150, 300, 450, 600, `DURATION=30s`, `PRE_ALLOCATED_VUS=200 MAX_VUS=2000`. 회원 = 쿠폰 수량 = `RATE × 30` (모든 요청이 발급되는 조건). `WARMUP=200`(별도 쿠폰). 비동기 방식은 확정이 끝날 때까지 결과 API 를 0.5초 간격으로 다시 조회(`CONFIRM_POLL_MS=500`)
- 순서: 설정마다 앱을 새로 띄우고 실험 API 의 `DELETE /lab/data` 로 실험 스키마와 Redis db 2 의 `coupon:*` 를 비운 뒤 150 → 300 → 450 → 600. 설정 순서는 비관적 락 → 동기 Lua → 동기 Lua(Hikari 4) → 비동기 → Pub/Sub → Stream. 이것을 2회
- 보낸 요청 = k6 가 시작한 요청 수, 못 보낸 요청 = k6 `dropped_iterations`(VU 2000개가 모두 응답을 기다리는 중이라 목표 속도대로 보내지 못한 요청)
- 409 1건은 k6 가 목표보다 1건 더 보내(예: 4501) 첫 회원이 두 번 요청된 것이다
- 발급 완료 req/s = 발급 수 / 확정까지. 확정까지 = 측정 시작부터 마지막 확정까지(비동기는 조회 간격 0.5초만큼 늦게 잡힌다). "보내기 끝났을 때 미완료" = 30초 보내기를 마친 뒤 첫 조회의 미완료(비동기 `pending`, Pub/Sub·Stream 은 Redis 에만 있는 회원)
- MySQL CPU = Docker API 의 컨테이너 누적 CPU 를 0.1초 간격으로 기록해, 측정 쿠폰 생성 시각부터 확정까지 구간의 평균과 1초 구간 최대. 100% = 1코어(컨테이너 제한)
- 실행 스크립트: `build/lab-tmp/exp7-load.sh`, 요약 `build/lab-tmp/load_report.py` (저장소 밖)
