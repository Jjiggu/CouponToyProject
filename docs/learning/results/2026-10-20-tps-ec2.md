# 쿠폰 1장 따라간 최대 속도 측정 원본 (2026-10-20, EC2): 앱·DB·k6 를 인스턴스로 나눠서

실행 조건
- 서울 리전, 세 대 같은 서브넷, Ubuntu 24.04.4 LTS (aarch64). db: c7g.large(2 vCPU, 4GiB, gp3 20GiB), app: c7g.xlarge(4 vCPU, 8GiB), k6: c7g.large. 보안 그룹은 SSH(내 IP)와 같은 그룹끼리만 허용
- db: 저장소 `docker-compose.yml` 의 mysql·redis 만. Mac 과 같은지 확인한 값: MySQL 8.0.36, 각 1 CPU / 1GB, `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, binlog 켜짐, 버퍼 풀 128MB, REPEATABLE-READ, Redis AOF·RDB 끔
- app: OpenJDK 17.0.20.1, Mac 과 같은 jar. 발행자(18080)와 Pub/Sub 구독자·Stream 소비자(18081). k6 v2.1.0 (linux/arm64)
- 실행: `WARM_RATE=50 RATES="100 120 140 160 180" PESSIMISTIC_RATES="60 80 100 120 140" performance/ec2/ec2.sh tps tps`. 설정마다 앱을 새로 띄우고 실험 데이터를 비운 뒤 초당 50건 30초 예열(버림), 각 속도 30초, 2회. 판정은 Mac 과 같다(정상 구간 5~28초)
- 표본: db 인스턴스에서 MySQL 컨테이너 CPU 0.1초, `issued_count`·`Com_commit` 1초(호스트의 `mysql` 클라이언트). app·k6 인스턴스 CPU 는 각 측정 앞뒤 `/proc/stat` 차이
- 요약 스크립트: `performance/ec2/tps_report.py`

## 로그 파일 동기화 시간 (performance_schema `file_summary_by_event_name`, 탐색 측정 중 조회)

`COUNT_MISC`·`SUM_TIMER_MISC` 는 쓰기·읽기가 아닌 파일 작업(대부분 fsync)이다. 컨테이너를 띄운 뒤 누적값이다(Mac 은 며칠 동안의 모든 실험, EC2 는 setup 과 탐색).

|---|---:|---:|
| redo 로그 `innodb_log_file` | 2.647ms (37324회) | 0.731ms (4201563회) |
| binlog | 2.835ms (17435회) | 0.696ms (2099497회) |
