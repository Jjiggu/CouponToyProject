# 6단계 HTTP 실행 원본 (2026-10-19): Redis Streams, 발행자·소비자 별도 프로세스

실행 조건
- 같은 jar 를 프로필만 바꿔 띄웠다. 발행자 `local`(18080), 소비자 `stream-consumer`(18081, 두 번째 18082). 소비자 프로세스마다 같은 그룹 소비자 4개(`consumer-{pid}-1~4`), pollTimeout 500ms, 한 번에 10건, 회수 1초마다·최소 유휴 5초, 전달 횟수 상한 3. 모두 `CouponToyProject_lab`, Redis db 2, Hikari 최대 10
- MySQL 8.0.36 (Docker 1 CPU / 1GB), Redis 7.2.13 (Docker 1 CPU / 1GB, AOF·RDB 끔), k6 v2.1.0, macOS 호스트 한 대
- k6 공통: `MEMBERS=1000 VUS=100 ITERATIONS=1000 WARMUP=200 SCENARIO=burst`. e1 `TOTAL_COUNT=100`, e2 `TOTAL_COUNT=1000`
- Stream 방식은 teardown 에서 `redisOnlyMembers` 가 0 이 되거나 10초 동안 줄지 않을 때까지 50ms 간격으로 기다린다. "마지막 응답 시점 미완료" 는 teardown 첫 조회의 `redisOnlyMembers`(비동기는 `pending`)
- 소비자 쪽 재처리·재시도·따로 보관은 소비자 로그의 `already issued`, `will retry`, `dead letter` 줄 수로 셌다(성공은 로그를 남기지 않고 DB 발급 행으로 본다)
- 순서: (1) 소비자 프로세스 1개로 회차마다 e1 `REDIS_STREAM` → e2 `REDIS_STREAM` → e2 `REDIS_STREAM_ATOMIC` → e2 `REDIS_ASYNC`(4단계, 같은 세션 비교) 3회 (2) 소비자 프로세스 2개로 e2 3회 (3) 소비자 없이 e2 1회, 그 뒤 소비자 시작 (4) 소비자 프로세스 종료 (5) 실제 프로세스 종료 지점
- 처음 실행에서는 회차 사이에 호스트 TIME_WAIT 가 100 아래로 줄기를 기다리는 장치(3단계부터 씀) 때문에 회차마다 최대 120초씩 기다렸다. 소비자 프로세스가 메시지가 없어도 새 Redis 연결을 계속 맺어 TIME_WAIT 가 내려가지 않았기 때문이다(맨 아래). 멈추고 기준을 1000 으로 올려 처음부터 다시 돌렸고, 아래는 다시 돈 결과다
- 실행 스크립트: `build/lab-tmp/exp6-http.sh`, `lab5.sh` (저장소 밖)

## (4) 소비자 프로세스 종료 → 새 소비자 프로세스 (e2, WARMUP=0)

발행자 결과 API 의 `QUEUED` 가 300 을 넘으면 소비자 JVM 에 신호를 보냈다. k6 가 끝난 뒤 새 소비자 프로세스(새 pid, 새 소비자 이름)를 띄우고 `redisOnlyMembers` 가 0 이 될 때까지 0.1초 간격으로 봤다.

## 소비자 프로세스의 Redis 연결
