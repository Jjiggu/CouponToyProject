# 4단계 k6 HTTP 실행 원본 (2026-10-19)

실행 조건 (3단계 k6 와 같은 환경)
- 앱: macOS 호스트에서 `./gradlew bootRun` (OpenJDK 17.0.19, 8 cores, CPU 제한 없음), 포트 18080, 프로필 local, `CouponToyProject_lab`, Redis db 2, SQL 로그 끔. Tomcat 200, Hikari 최대 10, Lettuce 기본 설정
- MySQL 8.0.36 (Docker 1 CPU / 1GB), Redis 7.2.13 (Docker 1 CPU / 1GB, AOF·RDB 끔), k6 v2.1.0
- 비동기 스레드 풀 기본: 작업 스레드(`coupon-issue-async-N`) 4, 큐 50000, AbortPolicy
- k6 공통: `MEMBERS=1000 VUS=100 ITERATIONS=1000 WARMUP=200`. e1 `SCENARIO=burst TOTAL_COUNT=100`, e2 `SCENARIO=burst TOTAL_COUNT=1000`, e3 `SCENARIO=duplicate TOTAL_COUNT=100`(회원 100명 × 10번)
- 순서: 앱 하나로 회차마다 e1 → e2 → e3, 각각 `REDIS_LUA`·`REDIS_ASYNC` 를 번갈아(홀수 회차 LUA 먼저, 짝수 회차 ASYNC 먼저). 그 뒤 큐 100, 작업 스레드 1, 작업 스레드 10 을 각각 앱을 새로 띄워 e2 `REDIS_ASYNC` 3회
- `REDIS_ASYNC` 는 워밍업 확정이 모두 끝난 뒤 측정을 시작하고, teardown 에서 `pending` 이 0 이 될 때까지 50ms 간격으로 결과 API 를 다시 조회한다. "확정까지" 는 측정 시작부터 그 시점까지(조회 간격만큼 늦게 잡힌다)
- 접수 처리량 = 요청 수 / 마지막 응답까지, 발급 완료 처리량 = 발급 수 / 확정까지. 동기 방식은 둘의 분모가 거의 같다
- "마지막 응답 시점 미완료" 는 teardown 첫 조회의 `pending` 이다
- 실행마다 호스트 TIME_WAIT 가 100 아래로 빠질 때까지 기다렸다(3단계와 같은 실행 스크립트)
- k6 종료 코드 99 는 기준값(`coupon_issue_http_duration` p95 < 500, 비동기는 < 100)을 넘은 것이다. 측정은 끝까지 했다
- 처음 돌린 27회는 결과 API 가 DB 를 요청 기록보다 먼저 읽는 순서 문제(확정 1000건인데 DB 998건으로 보인 회차가 있었다)와 워밍업 확정이 측정과 섞일 수 있는 문제가 있어 버리고, 고친 뒤 전부 다시 쟀다. 아래는 다시 잰 결과다
