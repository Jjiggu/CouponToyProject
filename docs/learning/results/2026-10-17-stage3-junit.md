# 3단계 JUnit 실행 원본 (2026-10-17): Redis SET 명령만 / MULTI/EXEC / WATCH / Lua

`./gradlew test --tests '*RedisReservationTest'` 가 `build/lab/stage3-redis.md` 에 남긴 내용을 그대로 옮겼다.

실행 조건
- Redis 7.2.13 (Docker, `io-threads=1`, `multiplexing_api=epoll`, AOF·RDB 저장 끔), 테스트는 db 1
- MySQL 8.0.36 (Docker, 1 CPU / 1GB), REPEATABLE READ, DB `CouponToyProject_test`
- 테스트 JVM: macOS 호스트, OpenJDK 17.0.19, 8 cores, Hikari 최대 풀 10, Lettuce 기본 설정(공유 커넥션, 커넥션 풀 없음)
- 동시 요청은 HTTP 없이 `LabService.issue()` 를 스레드에서 직접 호출. 스레드 수 = 요청 수
- WATCH 재시도 최대 10회(지연 없음)
- 실패 지점(`FailurePoints`)으로 실행 순서를 고정했다. 프로세스 강제 종료는 해당 지점에서 `Error` 를 던져 흉내 냈다(보상 코드가 실행되지 않고, 커밋 전 DB 트랜잭션은 롤백되며, 실행된 Redis 명령은 남는다). 실제 JVM 종료 실험은 [kill 원본](2026-10-17-stage3-kill.md).
- 같은 클래스를 3번 실행했다. 순서 고정 케이스의 결과는 3번 모두 같았다. 아래는 1회차 기록이다.
- 동시 요청의 `SOLD_OUT_AT_DB`(Redis 는 통과, DB 가 막음)는 실행마다 크게 달랐다. SET 명령만, 재고 10 / 요청 50 에서 회차별로 1회차 실행 6·5·9, 2회차 실행 18·37·10, 3회차 실행 23·40·40 건이었다. 2·3회차 실행의 해당 표는 맨 아래에 붙였다.
