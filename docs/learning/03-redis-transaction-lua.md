# 3단계: Redis 지급 처리 — SET 명령만 / MULTI/EXEC / WATCH / Lua

실행 원본 (2026-10-17): [JUnit](results/2026-10-17-stage3-junit.md), [k6](results/2026-10-17-stage3-k6.md), [실제 프로세스 강제 종료·Redis 명령 수](results/2026-10-17-stage3-kill.md) · 바꿔본 조건 (2026-10-19): [원본](results/2026-10-19-stage3-conditions.md)

## 1. 확인할 질문과 예상

질문
- Redis 는 명령을 하나씩 실행한다. 그러면 트랜잭션 없이 SET 명령만 따로 보내도 동시성 문제가 없는가? 여러 클라이언트 소켓을 한 스레드가 번갈아 처리하는 구조(I/O 멀티플렉싱)에서 명령 사이에 다른 요청이 끼어드는가?
- 현재 MULTI/EXEC 구현은 무엇을 보장하고 무엇을 보장하지 않는가? "명령을 묶어 실행" 과 "조건을 검사하고 바꾸기를 한 번에" 는 어떻게 다른가?
- Lua 와 WATCH 는 그 차이를 어떻게 메우는가? 대가는 무엇인가?
- Redis 와 MySQL 이 한 트랜잭션이 아닐 때 어떤 순서에서 둘이 어긋나는가? DB 의 조건부 UPDATE 와 UNIQUE 제약은 그중 무엇을 막는가?

실행 전 예상
- SET 명령만: 명령 하나(SADD)는 원자적이라 같은 회원 중복 지급 처리는 막는다. 하지만 SCARD 로 확인하고 SADD 로 넣는 사이에 다른 요청이 끼어들어 재고보다 많이 지급 처리할 것.
- MULTI/EXEC: SCARD 와 SADD 사이에는 아무것도 끼지 않는다. 하지만 SCARD 결과를 보고 SADD 를 할지 고를 수 없어 일단 넣고 되돌린다. 되돌리기(SREM) 전 틈에서 거짓 품절이나 영구히 남는 지급 처리가 생길 것.
- WATCH: 끼어들면 EXEC 가 무효가 되어 정확하겠지만, 경합이 심하면 재시도가 많을 것.
- Lua: 판단과 지급 처리가 한 번에 실행되어 Redis 안에서는 정확할 것. 그러나 Redis 지급 처리와 실제 지급 사이의 문제는 Lua 로도 해결되지 않을 것.

## 2. 구현과 명령 실행 순서

Redis 지급 처리 방식 네 가지([`CouponIssuedRedisRepository`](../../src/main/java/couponToy/CouponToyProject/CouponIssue/repository/CouponIssuedRedisRepository.java))는 모두 "이미 지급 처리됨 → 재고 소진 → 지급 처리" 순서로 판단하고, 원자성만 다르다. 이후 처리는 같다([`RedisIssueCouponService`](../../src/main/java/couponToy/CouponToyProject/CouponIssue/service/RedisIssueCouponService.java)).

```
[0] GET coupon:total:{id}                        총수량 (없으면 DB 에서 읽어 다시 넣음)
[1] Redis 지급 처리                               방식별 (아래 표)
[2] 실제 지급 (IssueConfirmService, 별도 트랜잭션) INSERT coupon_issues  ← UNIQUE(coupon_id, member_id)
                                                  UPDATE coupons SET issued_count = issued_count + 1
                                                   WHERE coupon_id = ? AND issued_count < total_count   ← 0건이면 SOLD_OUT_AT_DB
[3] [2] 가 실패하면 SREM 으로 Redis 지급 처리를 취소한다. 단 UNIQUE 위반(이미 지급된 회원)은 취소하지 않는다
```

| 방식 | 명령 | 끼어들 수 있는 곳 |
|---|---|---|
| SET 명령만 | `SISMEMBER` → (Java 확인) → `SCARD` → (Java 확인) → `SADD` | 명령과 명령 사이 어디든 |
| MULTI/EXEC (기존) | `MULTI`, `SCARD`(QUEUED), `SADD`(QUEUED), `EXEC` → Java 가 `[개수, 추가 여부]` 로 판단 → 재고 초과면 `SREM` | EXEC 와 SREM 사이. 이때 SET 에 재고보다 많은 회원이 들어 있다 |
| WATCH | `WATCH` → `SISMEMBER` → `SCARD` → `MULTI`, `SADD`, `EXEC` (감시한 키가 바뀌었으면 EXEC 가 실행되지 않음 → 처음부터 다시, 최대 10회) | 끼어들 수는 있지만 EXEC 가 무효가 된다 |
| Lua | `EVALSHA` 한 번 (스크립트 안에서 `SISMEMBER`, `SCARD`, `SADD`) | 없음. 스크립트가 도는 동안 다른 명령은 실행되지 않는다 |

**명령을 묶어 실행하는 것과 조건 검사·변경을 함께 하는 것은 다르다.** MULTI/EXEC 는 큐에 쌓인 명령들을 다른 클라이언트 명령 없이 연달아 실행해 줄 뿐이다. 큐에 넣는 시점에는 앞 명령의 결과를 알 수 없으므로 "재고가 남았으면 넣는다" 를 표현할 수 없다. 그래서 일단 넣고 Java 에서 보고 되돌린다. Lua 는 앞 명령 결과로 분기할 수 있어서 판단과 변경이 한 실행 안에 들어간다. WATCH 는 MULTI/EXEC 에 "읽은 뒤 바뀌었으면 취소" 조건을 붙인 낙관적 방식이다.

**Redis 의 실행 구조 (이 환경)**: Redis 7.2.13, `io-threads=1`, `multiplexing_api=epoll`. 메인 스레드 하나가 epoll 로 준비된 소켓을 돌며 명령을 하나씩 끝까지 실행한다. 명령 하나는 원자적이지만, 한 클라이언트가 보낸 두 명령 사이에는 다른 소켓의 명령이 실행될 수 있다. `multiplexing_api` 는 설정이 아니라 빌드할 때 OS 에 맞춰 정해진 값이다(Linux 는 epoll, macOS 는 kqueue. 지금은 Docker 의 Linux VM 이라 epoll). `io-threads` 는 기본값 1(메인 스레드만)이다. 늘려도 기본으로는 응답 쓰기만 나누고, 읽기·파싱까지 나누려면 `io-threads-do-reads yes` 를 함께 켜야 한다. 어느 쪽이든 명령 실행은 메인 스레드이고, 연결 수가 적으면 Redis 가 스레드 I/O 를 스스로 끈다는 것이 Redis 설정 파일(redis.conf) 설명이다(4-8 에서 켜고 확인했다). 앱 쪽 Lettuce 는 기본 설정에서 모든 스레드가 TCP 연결 하나를 같이 쓴다. 그래서 여러 스레드의 명령이 한 연결 위에서도 섞인다.

기존 구현에서 바꾼 것 (`IssueCouponService` → `RedisIssueCouponService`)

| 기존 | 문제 | 바꾼 것 |
|---|---|---|
| Redis 지급 처리가 DB `@Transactional` 메서드 안에 있었다 | DB 가 롤백돼도 Redis 는 그대로다. Redis 왕복 동안 DB 커넥션을 붙잡는다 | Redis 지급 처리는 트랜잭션 밖, 실제 지급만 별도 트랜잭션 |
| 보상(SREM)이 메서드 안 `try` 에만 있었다 | 메서드가 끝난 뒤 커밋이 실패하면 Redis 지급 처리만 남는다 | 커밋까지 끝난 `confirm()` 을 `try` 로 감쌌다 |
| DB UNIQUE 위반에도 SREM 했다 | 실제로 지급받은 회원을 Redis 가 잊는다(코드로 확인, 기존 코드로 실행하지는 않음) | UNIQUE 위반이면 Redis 지급 처리를 남긴다 (4-6) |
| 실제 지급 실패와 Redis 품절이 같은 예외였다 | Redis 와 DB 가 어긋난 것을 구분할 수 없다 | DB 조건부 UPDATE 가 막으면 `SOLD_OUT_AT_DB` |
| 쓰지 않는 쿠폰 SELECT, 메트릭 래퍼 | 흐름이 잘 안 보인다 | 제거 |

실패를 제어하는 장치: [`FailurePoints`](../../src/main/java/couponToy/CouponToyProject/global/failure/FailurePoints.java). 평소에는 아무 일도 하지 않는다. 테스트가 회원 단위로 지점에 동작을 걸어, 그 요청을 멈추거나(실행 순서 고정), 실패시키거나(실제 지급 실패), `Error` 를 던져 프로세스 종료를 흉내 낸다(보상이 실행되지 않음). 앱을 `LAB_HALT_AT=<지점>` 으로 띄우면 그 지점에서 JVM 이 실제로 즉시 종료된다.

실험 API `method`: `REDIS_SET_ONLY`, `REDIS_MULTI_EXEC`, `REDIS_WATCH`, `REDIS_LUA` (기존 `REDIS_TRANSACTIONAL` 은 `REDIS_MULTI_EXEC` 로 바뀌었다). 결과 API 에 `redisOnlyMembers`(Redis 에만 있는 회원), `dbOnlyMembers`(DB 에만 있는 회원)를 추가했다.

## 4. 관찰 결과와 원인

### 4-1. SET 명령만 쓰면 명령 사이에 끼어든다 (질문에 대한 답)

순서 고정 (재고 1, 3회 같은 결과)

| 방식 | 실행 순서 | 결과 |
|---|---|---|
| SET 명령만 | A 가 `SISMEMBER`, `SCARD`(0) 확인 후 멈춤 → B 가 끝까지 실행(지급) → A 의 `SADD` | A 도 지급 처리됨. **A 지급 처리 직후 SCARD 2 (재고 1)**. DB 조건부 UPDATE 가 A 를 막음(`SOLD_OUT_AT_DB`), 보상 SREM |
| WATCH | A 가 `WATCH`, 확인 후 멈춤 → B 가 끝까지 실행 → A 의 `EXEC` | A 의 EXEC 가 무효 → 두 번째 시도에서 다시 읽고 `SOLD_OUT`. SCARD 는 1 을 넘지 않음 |
| MULTI/EXEC, Lua | 확인과 지급 처리 사이에 틈이 없다 | 해당 없음 |

동시 요청에서도 실제로 일어났다
- JUnit(요청 50, 재고 10): SET 명령만은 3번 실행, 회차 9번 모두 Redis 가 재고보다 많이 지급 처리했고 DB 가 막았다. **회차당 5~40건**이 `SOLD_OUT_AT_DB` 였다. 40건이면 거의 모든 요청이 SCARD 를 마친 뒤에 SADD 를 했다는 뜻이다. Lettuce 공유 연결 위에서 50개 스레드의 명령이 같은 걸음으로 나간 것으로 보인다.
- HTTP(요청 1000, 재고 100, 3회): 회차당 0~4건. 요청이 시간상 퍼져 있어 경계에서 겹치는 일이 드물었다.
- 같은 회원 중복은 SET 명령만으로도 한 번도 두 번 지급 처리되지 않았다(JUnit 회원 10명 × 5번에서 매 회차 `DUPLICATE` 40). `SADD` 하나가 "없으면 넣고 결과를 알려 주는" 원자적 명령이기 때문이다.
- MULTI/EXEC, WATCH, Lua 는 모든 실행에서 `SOLD_OUT_AT_DB` 0 건이었다.

정리: Redis 가 명령을 하나씩 실행한다는 것은 "명령 하나" 의 원자성이다. 확인 명령과 변경 명령이 따로 가면, I/O 멀티플렉싱으로 다른 클라이언트의 명령이 그 사이에 실행된다. 앱 쪽 공유 연결도 같은 효과를 낸다.

### 4-2. MULTI/EXEC 의 되돌리기(SREM) 전 틈 (재고 1, 3회 같은 결과)

**다른 회원의 Redis 지급 처리 취소와 겹치면 거짓 품절이 생긴다**

순서: A 지급 처리 → B 요청 → A 의 실제 지급이 실패해 지급 처리 취소 → C 요청 → B 마무리. B 는 재고 초과라 SREM 직전에 멈춰 둔다.

| 방식 | B 처리 중 Redis | A 취소 직후 Redis | B | C | 최종 지급 |
|---|---|---|---|---|---:|
| MULTI/EXEC | {A, B} | {B} | 품절 | **품절** | **0** |
| Lua / SET 명령만 / WATCH | {A} | {} | 품절 | 성공 | 1 |

MULTI/EXEC 에서는 B 가 재고 초과로 판정된 뒤에도 SREM 전까지 SET 에 남아 있었다. 그래서 A 가 취소돼 자리가 비었는데도 C 의 EXEC 가 개수 1 을 보고 품절이 됐다. 마지막 요청이 C 였다면 쿠폰은 한 장도 나가지 않는다.

**되돌리기 전에 프로세스가 죽으면 쿠폰 없는 회원이 Redis 에 영구히 남는다**

| 방식 | A 지급 후 B 요청 | 직후 SCARD | B 재요청 |
|---|---|---:|---|
| MULTI/EXEC (SREM 전 종료) | 종료 | **2 (재고 1)** | **`DUPLICATE` (쿠폰이 없는데 이미 지급)** |
| Lua | 품절 | 1 | 품절 |

실제 JVM 강제 종료(`LAB_HALT_AT=MULTI_EXEC_BEFORE_SREM`)로도 같았다. B 요청 중 JVM 이 종료 코드 137 로 끝났고 응답은 오지 않았다. Redis 에는 {A, B}, DB 에는 A 만 남았다. 재시작 후 B 는 409 "이미 쿠폰 발급 받은 사용자입니다" 를 받았다.

### 4-3. Redis 지급 처리 뒤 실제 지급 전 실패와 프로세스 종료 (네 방식 공통, 재고 1, 3회 같은 결과)

| 실패 | 네 방식 모두 | 직후 Redis 에 A | A 재요청 | B 요청 | 최종 |
|---|---|---|---|---|---|
| 실제 지급 실패 (예외) | A `ERROR`, 보상 SREM | 없음 | 성공 | 품절 | 지급 1, Redis = DB |
| Redis 지급 처리 직후 프로세스 종료 | A 응답 없음 | **남음** | **`DUPLICATE`** | **품절** | **지급 0**, Redis 에만 A |
| DB 커밋 직전 프로세스 종료 (Lua) | DB 트랜잭션은 롤백 | **남음** | `DUPLICATE` | 품절 | 지급 0 |

실제 JVM 강제 종료(`LAB_HALT_AT=AFTER_RESERVE`, Lua)로도 같았다. Redis {A}, DB 0 이었고, 재시작 후 A 는 "이미 발급", B 는 "품절" 을 받았다. 쿠폰은 한 장도 나가지 않았다.

Lua 는 Redis 안의 판단을 원자적으로 만들 뿐, Redis 지급 처리와 실제 지급을 묶어 주지 않는다. Redis 지급 처리 뒤 프로세스가 죽으면 그 지급 처리가 왜 남았는지 판단할 근거가 Redis 와 DB 어디에도 없다.

### 4-4. Redis 지급 처리 취소 전 같은 회원의 재요청 (Lua, 재고 1, 3회 같은 결과)

A 의 실제 지급이 실패한 뒤 SREM 직전에 멈춰 두었다. 멈춘 동안 A 는 다시 요청하면 `DUPLICATE`(쿠폰이 없는데 이미 지급), B 는 `SOLD_OUT` 을 받았다. SREM 이 끝난 뒤 A 의 재요청은 성공했다. 보상이 끝나기 전에는 Redis 가 "아직 실제 지급되지 않은 Redis 지급 처리" 와 "실제 지급 완료" 를 구분하지 못한다.

### 4-6. Redis 가 지급 기록을 잃은 뒤 재요청 (Lua, 재고 10, 3회 같은 결과)

|---|---|---|---|---|

JUnit(재고 10, 요청 50)에서 SET 명령만의 과다 지급 처리는 io-threads 1 에서 회차당 39~40건, 3 에서 6~16건으로 둘 다 났다. MULTI/EXEC·Lua 는 0건이었다.

- I/O 스레드를 켜도 SET 명령만의 끼어들기는 그대로 났다. I/O 스레드는 소켓 읽기와 응답 쓰기만 나눠 맡고, 명령 실행은 여전히 메인 스레드 하나다. 끼어들기는 명령과 명령 사이에서 생기므로 I/O 스레드와 관계가 없다. 39~40 과 6~16 의 차이는 10/17 에 같은 설정에서 본 편차(5~40) 안이라 I/O 스레드 효과로 보지 않는다.
- SET 명령만과 Lua 에서는 I/O 스레드가 한 번도 일하지 않았다. 둘은 Lettuce 공유 연결 하나로 나간다. Redis 는 응답을 기다리는 클라이언트가 `io-threads × 2` 보다 적으면 I/O 스레드를 멈추고 메인 스레드로 처리한다(Redis 7.2 `networking.c` 의 `stopThreadedIOIfNeeded`). 요청마다 새 연결을 여는 MULTI/EXEC 만 I/O 스레드를 썼다.
- 처리량과 지연은 모든 방식에서 범위가 겹쳤다. 이 실험의 병목은 Redis I/O 가 아니었다.

**Redis 영속화** (별도 컨테이너. `redis-cli` 로 지급 처리 100건을 `SADD` 로 하나씩 넣은 직후 재시작)

| 설정 | `docker restart` (SIGTERM, 정상 종료) 뒤 남은 지급 처리 | `docker kill -s KILL` (강제 종료) 뒤 남은 지급 처리 |
|---|---|---|
| 지금 프로젝트 설정 `--appendonly no --save ""` | **0 / 100** | **0 / 100** |
| Redis 기본 RDB (`save 3600 1 300 100 60 10000`) | 100 / 100 (종료하며 RDB 저장) | **0 / 100** |
| AOF `appendfsync everysec` | 100 / 100 | 100 / 100 |

- 지금 설정에서는 Redis 가 재시작되기만 해도 지급 처리가 모두 사라진다. 그 뒤 상황은 4-6(키 삭제로 흉내 냄)과 같다. 이미 지급된 회원은 Redis 를 통과하고 DB UNIQUE 가 막는다. 남은 재고는 DB 조건부 UPDATE 가 막는다.
- RDB 는 정상 종료할 때만 저장했다. 강제 종료하면 마지막 저장 이후의 쓰기를 잃었다. 100건 변경으로는 `300 100` 규칙의 300초가 차지 않았다.
- AOF everysec 는 강제 종료 직후에도 100건이 남았다. Redis 는 응답 전에 쓰기를 OS 로 넘기고 fsync 만 1초마다 한다. 그래서 프로세스만 죽으면 OS 가 가진 데이터는 남는다. OS 나 머신이 죽으면 마지막 1초 안의 쓰기를 잃을 수 있다(재현하지 않았다).
- 어느 설정이든 Redis 가 보존하는 것은 지급 처리뿐이다. 4-3 처럼 Redis 지급 처리 뒤에 앱이 죽은 경우를 구분해 주지 않는다.

## 5. 보장하는 범위와 해결하지 못한 문제

DB 쪽 방어선이 막는 것과 못 막는 것
- 조건부 UPDATE(`issued_count < total_count`): Redis 가 재고보다 많이 지급 처리해도(SET 명령만, 5~40건) DB 지급은 재고를 넘지 않았다.
- UNIQUE(coupon_id, member_id): Redis 가 지급 기록을 잃어도 같은 회원의 두 번째 행은 들어가지 않았다.
- 못 막는 것: 새어 나간 지급 처리(쿠폰 없는 회원의 `DUPLICATE`, 아무도 못 받는 재고), 거짓 품절, 진입 순서와 다른 당첨. 이때도 DB 기준 검사는 모두 통과했다(4-2, 4-3 의 결과 API `checks` 는 모두 true, `redisOnlyMembers` 1). **DB 가 오류를 막았다고 Redis 구현이 맞는 것은 아니다.**

해결하지 못한 문제
- Redis 와 MySQL 은 하나의 트랜잭션이 아니다. Redis 지급 처리와 실제 지급 사이에 프로세스가 죽으면 Redis 지급 처리만 남고, 그 지급 처리를 취소할 근거가 어디에도 기록되지 않는다.
- 보상 SREM 은 "실제 지급 실패" 를 전제로 한다. 커밋은 됐는데 응답만 잃은 경우에도 SREM 하므로, 그때는 Redis 가 실제로 지급받은 회원을 잊는다(재현하지 않았다).
- 보상이 끝나기 전에는 Redis 가 "실제 지급 전 Redis 지급 처리" 와 "실제 지급 완료" 를 구분하지 못한다(4-4).
- 지금 Redis 설정(AOF·RDB 끔)에서는 Redis 재시작만으로 지급 처리가 모두 사라진다. AOF everysec 로 프로세스 종료는 견뎠지만 OS·머신 장애는 확인하지 않았다(4-8).
- MULTI/EXEC·WATCH 는 커넥션 풀이 없으면 요청(시도)마다 연결을 새로 맺는다. 경합이 심하면 끊긴 연결(TIME_WAIT)이 호스트 임시 포트 수만큼 쌓였고, 그 회차에서 Redis 연결이 실패했다(4-8).
- 사용자 응답은 여전히 실제 지급이 끝날 때까지 기다린다. 재고 1000 처럼 전원에게 지급되는 경우에는 처리량이 DB 쿠폰 행 UPDATE 줄서기에 묶였다.

## 6. 다음 단계로 넘어가는 이유

Lua 로 "Redis 안에서의 판단" 은 정확해졌다. 4~6단계의 공통 기준으로 Lua 지급 처리(`reserveWithLua`)와 같은 실제 지급(`IssueConfirmService`)을 쓴다.

남은 문제는 둘 사이다. 응답이 실제 지급까지 기다려야 하고, Redis 지급 처리와 실제 지급 사이에 프로세스가 죽으면 지급 처리가 새어 나간다. 4단계부터는 이 둘 사이에서 작업을 전달·실행·복구하는 방식을 바꾼다.
- 4단계 `@Async`: Redis 지급 처리 후 바로 202 로 응답하고 실제 지급을 같은 프로세스의 스레드 풀로 넘긴다. 지급 성공 응답과 실제 지급 완료가 갈라진다. 큐가 넘치거나 프로세스가 죽으면 작업은 어디서 사라지는가?
- 5·6단계: 작업을 프로세스 밖(Redis Pub/Sub, Streams)으로 옮기면 유실과 재처리는 어떻게 달라지는가?
