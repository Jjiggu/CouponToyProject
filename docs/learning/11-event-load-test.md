# 선착순 쿠폰 이벤트 오픈 시나리오: 예상 최대 트래픽에서 안정적으로 동작하는가

실행 원본 (2026-10-25): [EC2](results/2026-10-25-event-ec2.md). 방식은 10단계(`REDIS_WRITE_BEHIND_NO_TX`)

## 1. 질문과 예상

7~10단계는 "모든 요청이 발급되는" 조건에서 한계를 쟀다. 실제 선착순 쿠폰은 재고가 참여자보다 훨씬 적고, 트래픽 모양도 다르다. 이번에는 그 모양을 흉내 내 **예상 최대 트래픽에서 오래 버티는지**, 그리고 끝난 뒤 **접수 기록과 발급 기록이 정확히 맞는지** 확인한다.

예상
- 재고 7000 은 오픈 몇 초 안에 다 나간다. 그 뒤 거의 모든 요청은 409(품절·이미 받음)다
- 쓰기(적재)는 처음 몇 초에 몰리고, 그 뒤 부담은 요청마다 하는 회원 확인 SELECT 와 Redis Lua 다. 최대 초당 4000건이면 MySQL CPU 는 60% 안팎이다(회원 확인 약 140µs × 4000)

## 2. 시나리오

| 구간 | 속도 | 시간 | 흉내 내는 것 |
|---|---|---|---|
| 오픈 | 0 → 초당 4000 | 10초 | 정각 몰림 |
| 몰림 유지 | 초당 4000 | 2분 | 품절 뒤에도 계속 누름 |
| 빠져나감 | 4000 → 800 | 3분 | 품절 확인 후 이탈 |
| 꼬리 | 초당 800 | 5분 | 늦게 온 사람 |

- 재고 7000, 회원 10만 명(경쟁률 약 14:1). 요청마다 회원을 무작위로 골라 같은 회원이 여러 번 누른다(연타)
- 요청의 5% 는 같은 회원이 같은 요청을 동시에 두 번 보낸다(더블클릭). 한 사람에게 두 장이 나가지 않는지 본다
- 최대치 4000 은 10단계에서 잰 "따라간 최대 속도" 4800 의 약 80% 다. 한계에 여유를 둔 예상 최대치로 잡았다
- 판정 기준(미리 정함): 분마다 서버 오류 0, 응답 p95 < 100ms, MySQL CPU < 90%(7~10단계에서 95% 를 넘으면 무너졌다), 전체에서 k6 가 못 보낸 요청 0. 최종 정합성 항목이 모두 맞을 것

```bash
performance/ec2/ec2.sh event event   # 스크립트: performance/k6/coupon-event.js, performance/ec2/event_report.py
```

- **재고는 오픈 6.0초에 다 나갔고, DB 적재는 7.1초에 끝났다**(1초 표본이라 ±1초). Redis 명단과 DB 행의 차이(미적재)는 최대 146건이었고, 부하가 끝난 뒤 적재 완료를 기다린 시간은 1초였다
- 몰림 구간(초당 4000)에서 MySQL CPU 58~62%, 응답 p95 4.2~4.9ms. 예상대로 쓰기는 처음 몇 초뿐이고, 남은 부담은 회원 확인 SELECT 다(요청당 MySQL CPU 0.62 ÷ 4000 ≈ 155µs)
- 앱 java 메모리(두 JVM 합)가 958MB → 1319MB 로 늘었다가 6분부터 1315MB 안팎에서 멈췄다. 늘어난 몫의 대부분은 실험 API 가 요청마다 남기는 기록(`IssueRequestLog`, 이번에 123만 건)으로 본다. 서비스 코드가 아니라 측정용 기록이다(나누어 재지 않음)
- k6 인스턴스 CPU 가 최대 48% 로, 부하 발생기가 한계는 아니었다

거절 1,223,712 건은 서버 기록으로 품절 1,137,373 건과 이미 받음 86,339 건이었다. 더블클릭 58,715 쌍이 섞였어도 한 회원에게 두 장이 나가지 않았다.

## 4. 보장 범위와 해결하지 못한 문제

- 이 결과는 "재고가 적고 거절이 대부분인" 이벤트 모양에서의 안정성이다. 쓰기가 계속 많은 조건의 한계는 8·10단계를 본다(10단계 4800)
- 정합성은 Redis 가 기록을 잃지 않는다는 전제 위에 있다(9단계). 이번 실행에서 Redis 는 영속화를 끈 채였고, 장애는 넣지 않았다
- 실험 API 의 요청 기록이 메모리에 쌓여 앱 메모리가 늘었다. 더 길게 돌리면 이 기록이 먼저 문제가 될 수 있다. 서비스 코드에는 없는 부분이다
- 정각 이전 대기(페이지 새로고침 등), 로그인, 쿠폰 조회 같은 다른 요청은 넣지 않았다. 발급 API 하나만 보낸다
- 1회 실행이다. 최대치를 올려 보거나(10단계 한계 4800 근처), 오픈 구간을 더 가파르게(예: 1초 만에 최대치) 하면 결과가 달라질 수 있다
