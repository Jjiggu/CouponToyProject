# 2단계: 비관적 락과 낙관적 락

실행 원본 (2026-10-17): [JUnit](results/2026-10-17-stage2-junit.md), [k6](results/2026-10-17-stage2-k6.md), [락 부여 순서(CATS) 보완](results/2026-10-17-stage2-cats.md)

## 1. 확인할 질문과 예상

질문
- 1단계 SERIALIZABLE 의 데드락은 "S 락을 쥔 채 X 락으로 올리는" 구조에서 났다. 처음부터 X 락으로 읽으면(비관적 락) 데드락 대신 줄서기가 되는가? 락은 언제 잡고, 기다리고, 놓는가?
- 락 없이 읽고 커밋 때 버전을 검사하면(낙관적 락) 충돌을 언제, 어떻게 알아채는가? 재시도가 없을 때와 제한된 재시도가 있을 때 지급 건수, 지연, 순서는 어떻게 다른가?
- 버전 검사를 거치지 않는 쓰기가 섞이면 어떻게 되는가?
- 먼저 온 요청이 당첨되는가? 특정 요청만 계속 지는가?
- 비관적 락에서 락이 풀리면 대기자 중 누가 먼저 받는가? MySQL 8.0.20 부터 InnoDB 는 FIFO 가 아니라 CATS 로 고른다.

실행 전 예상 (순서 고정·끼어든 쓰기 케이스는 테스트 기대값 표에 먼저 적고 실행했다)
- 비관적 락: 모든 요청이 쿠폰 행 X 락 앞에서 줄을 선다. 데드락 없이 정합성을 지키고, 유효 요청이 충분하면 재고만큼 지급한다.
- 비관적 락, 같은 회원 2번: 앱의 중복 확인이 아니라 UNIQUE 제약이 막을 것. RR 스냅샷은 첫 일반 SELECT(회원 조회) 때 잡히는데, 이는 락을 기다리기 전이다. 그래서 앞선 트랜잭션이 커밋한 지급 행이 중복 확인 SELECT 에 보이지 않을 것이다.
- 낙관적 락, 재시도 없음: 충돌한 요청이 그대로 실패한다. 1단계 SERIALIZABLE 처럼 동시에 열린 트랜잭션 묶음마다 1건 정도만 성공할 것.
- 낙관적 락, 재시도: 성공은 늘지만 지연이 늘고 당첨 순서가 섞일 것.
- 벌크 UPDATE 나 `Coupon` 엔티티로 쓰면 version 이 오르지 않으므로, 낙관적 락이 그 변경을 감지하지 못하고 덮어쓸 것.
- CATS (보완 실험): 쿠폰 행 대기자들이 다른 락을 쥐지 않으면 가중치가 같아 오래 기다린 순서로 넘어갈 것. 늦게 온 대기자가 다른 트랜잭션을 막고 있으면 그쪽이 먼저 받을 것.

## 2. 구현과 실행 순서

비교 조건: 세 방식 모두 회원 조회 → 쿠폰 조회 → 중복 확인 → `increaseIssueAmount()` → 저장 순서이고, 격리 수준은 MySQL 기본값 REPEATABLE READ 다. 차이는 쿠폰을 읽는 방법과 충돌을 처리하는 방법뿐이다.

비관적 락: 기존 [`PessimisticIssueCouponService`](../../src/main/java/couponToy/CouponToyProject/CouponIssue/service/PessimisticIssueCouponService.java) 를 그대로 쓴다.

| 순서 | SQL | 락 |
|---|---|---|
| 1 | `select ... from members where member_id=?` | 없음. **이 순간 RR 스냅샷이 만들어진다** |
| 2 | `select ... from coupons where coupon_id=? for update` | 쿠폰 행 `X,REC_NOT_GAP`. 다른 트랜잭션이 쥐고 있으면 **여기서 기다린다** |
| 3 | `select issued_id from coupon_issues where member_id=? and coupon_id=? limit ?` | 없음. 1번 스냅샷으로 읽는다 |
| 4 | `insert into coupon_issues ...` | |
| 5 | `update coupons set ..., issued_count=? where coupon_id=?` | 이미 X 락을 쥐고 있어 기다리지 않는다 |
| 6 | commit | **여기서 X 락을 놓는다.** 대기자 중 하나가 2번을 통과한다 |

누가 다음에 락을 받는가: MySQL 8.0.20 부터 InnoDB 는 FIFO 대신 CATS(Contention-Aware Transaction Scheduling)만 쓴다. 대기자마다 "자기가 막고 있는 트랜잭션 수"로 가중치를 매기고, 가중치가 큰 쪽에 먼저 준다. 가중치가 같으면 오래 기다린 쪽이 먼저다. 가중치는 `information_schema.INNODB_TRX.TRX_SCHEDULE_WEIGHT` 에서 `LOCK WAIT` 상태일 때만 보인다([MySQL 문서](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-scheduling.html)). 그래서 비관적 락의 "줄"은 도착 순서가 아니라 가중치 순서다. InnoDB 소스(`lock0wait.cc`) 주석 기준으로, 대기자는 모두 가중치 1 에서 시작하고 기다리는 쪽의 가중치가 자기가 기다리는 트랜잭션에 더해진다. 아주 오래 기다린 대기자는 가산점을 받아 무한히 밀리지 않는다(이 가산점은 측정하지 않았다). 가중치는 백그라운드 스레드가 대기 그래프를 주기적으로 분석해 갱신한다.

낙관적 락: [`VersionedCoupon`](../../src/main/java/couponToy/CouponToyProject/Coupon/model/VersionedCoupon.java) 은 같은 `coupons` 테이블에 `@Version` 을 붙인 별도 매핑이다. `Coupon` 에 넣으면 1단계와 비관적 락 구현까지 낙관적 락이 되므로 분리했다. `version` 컬럼은 `bigint default 0 not null` 이고, `Coupon` 으로 INSERT 하면 0 이 들어간다. 서비스는 [`OptimisticIssueCouponService`](../../src/main/java/couponToy/CouponToyProject/CouponIssue/service/OptimisticIssueCouponService.java) 다.

| 순서 | SQL | 락 |
|---|---|---|
| 1 | `select ... from members ...` | 없음 |
| 2 | `select ... from coupons where coupon_id=?` | **없음.** 이때 읽은 `version` 이 검사 기준이다 |
| 3 | 중복 확인 SELECT | 없음 |
| 4 | `insert into coupon_issues ...` | |
| 5 | 커밋 직전 flush: `update coupons set ..., version=v+1 where coupon_id=? and version=v` | 쿠폰 행 X 락. **낙관적 락도 여기서는 다른 트랜잭션의 UPDATE 를 기다린다** |
| 6 | 영향 행이 0 이면 `ObjectOptimisticLockingFailureException` → 롤백(4번 INSERT 도 되돌림) | |

제한된 재시도 (`issueWithRetry`)
- 버전 충돌일 때만 다시 시도한다. 중복, 품절, 데드락은 재시도하지 않는다.
- 시도마다 `TransactionTemplate` 으로 새 트랜잭션과 새 영속성 컨텍스트를 연다. 그래서 2번에서 최신 `version` 과 `issued_count` 를 다시 읽는다. 바깥 트랜잭션 안에서 부르면 모든 시도가 같은 영속성 컨텍스트에서 옛 값을 다시 읽게 되므로 `IllegalStateException` 으로 막았다.
- 기본값은 최대 5회, 지연은 `0 ~ min(100, 10 × 2^(n-1))` ms 중 무작위(지수 증가 + 전체 지터)다. `coupon.issue.optimistic.*` 설정이나 환경변수로 바꾼다.

기존 재시도 AOP(`@Retry`, `OptimisticLockRetryAspect`)는 호출처가 없어 삭제했다. 쓰지 않은 이유는 다음과 같다.
- 최대 1000회 × 100ms 고정 지연이라, 요청 하나가 최대 100초 동안 스레드와 커넥션 대기열을 붙잡는다.
- 지연이 고정이라, 함께 충돌한 요청들이 같은 순간에 다시 충돌한다.
- 애노테이션 기반이라 호출하는 쪽에서 재시도가 보이지 않는다. 바깥 트랜잭션 안에서 불리면 재시도가 같은 트랜잭션 안에서 돈다. 다만 advice 순서(`LOWEST_PRECEDENCE - 1`)는 트랜잭션 바깥에서 재시도하도록 맞게 잡혀 있었다.

실험 API: `method` 에 `PESSIMISTIC`, `OPTIMISTIC`, `OPTIMISTIC_RETRY`. 결과 API 의 `attempts` 에 요청별 시도 분포, 총 시도 수, 버전 충돌 수가 나온다. 버전 충돌은 데드락처럼 재시도하면 성공할 수 있는 실패라서 HTTP 503 이다.

## 4. 관찰 결과와 원인

### 4-1. 순서를 고정한 두 요청 (3회 반복, 매번 같은 결과)

1단계와 같은 하네스로 확인했다. 별도 커넥션이 쿠폰 행을 잡은 동안 두 요청을 출발시키고, 둘 다 대기에 들어간 것을 확인한 뒤 놓아준다.

| 경우 | 비관적 락 | 낙관적 락 | 낙관적 락 + 재시도 |
|---|---|---|---|
| 대기 위치 | `select ... for update` 에서 `X,REC_NOT_GAP` | 커밋 직전 `update ... and version=0` 에서 `X,REC_NOT_GAP` | 같음 |
| 재고 1, 2명 | 성공 + `SOLD_OUT` | 성공 + `OPTIMISTIC_CONFLICT` | 성공 + `SOLD_OUT`(두 번째 시도) |
| 재고 10, 2명 | **둘 다 성공**, 행 2 / `issued_count` 2 | 성공 + `OPTIMISTIC_CONFLICT` (재고가 남았는데 실패) | **둘 다 성공**, 시도 `{1=1, 2=1}` |
| 같은 회원 2번 | 성공 + **`UNIQUE_VIOLATION`** | 성공 + `UNIQUE_VIOLATION` | 같음 (UNIQUE 위반은 재시도하지 않음) |

- 비관적 락은 데드락이 없다. 두 요청이 2번 SQL 에서 X 락을 차례로 얻으므로, 뒤의 요청은 앞의 커밋 결과(`issued_count`)를 정확히 읽는다.
- 낙관적 락의 충돌은 읽을 때가 아니라 커밋 직전 UPDATE 에서 드러난다. 두 번째 요청은 첫 번째 요청의 UPDATE 가 끝나기를 X 락으로 기다린다. 그다음 `version=0` 조건이 0 행에 맞아 롤백된다.
- 비관적 락의 같은 회원 케이스는 예상대로 UNIQUE 제약이 막았다(`DataIntegrityViolationException`). 두 번째 요청은 락을 얻은 뒤 중복 확인 SELECT 를 했지만, 그 SELECT 는 락을 기다리기 전에 만든 스냅샷을 읽어서 앞선 요청의 지급 행을 보지 못했다. 쿠폰은 `FOR UPDATE`(최신 값을 읽는 잠금 읽기)라 정확했지만, 같은 트랜잭션의 일반 SELECT 는 옛 스냅샷을 읽었다.

### 4-2. 버전 검사를 거치지 않는 쓰기 (3회 반복, 매번 같은 결과)

다른 트랜잭션이 쿠폰 행에 쓰고 커밋하기 전에 낙관적 요청이 읽는다. 그 쓰기가 커밋된 뒤에야 낙관적 요청이 `update ... and version=0` 을 실행한다. 정상이라면 `issued_count` = 끼어든 쓰기 1 + 요청 성공 시 1 이다.

| 끼어든 쓰기 | 요청 | 결과 | 최종 `issued_count` | version |
|---|---|---|---|---:|
| `VersionedCoupon` 증가 (version 올림) | 낙관적 | `OPTIMISTIC_CONFLICT` | 1 (정상 1) | 1 |
| 같음 | 낙관적 + 재시도 | 두 번째 시도에 성공 | 2 (정상 2) | 2 |
| `CouponRepository.increaseIssuedCount` (JPQL 벌크 UPDATE) | 낙관적 | **성공** | **1 (정상 2)** | 1 |
| `Coupon` 엔티티 dirty checking | 낙관적 | **성공** | **1 (정상 2)** | 1 |

- 버전 검사는 version 을 올리는 쓰기끼리만 충돌을 잡는다. 벌크 UPDATE 와 `Coupon` 엔티티 쓰기는 version 을 그대로 두므로, 낙관적 요청이 그 사이의 증가를 덮어썼다. 충돌도 예외도 없이 갱신 손실이 났다.
- 재시도한 경우 두 번째 시도가 최신 `version=1`, `issued_count=1` 을 다시 읽어 2 로 올렸다. 재시도가 새 트랜잭션에서 최신 데이터로 수행된다는 확인이다.

### 4-3. 동시 요청 (JUnit, 요청 50건, 스레드 50, Hikari 10, 3회)

| 시나리오 | 비관적 락 | 낙관적 락 | 낙관적 락 + 재시도(최대 5) |
|---|---|---|---|
| 재고 10, 회원 50명 | 10 지급 / 품절 40. 먼저 온 10명 중 당첨 10. 서버 p95 76~90ms | 6 지급 / 충돌 44. 먼저 온 10명 중 1 | 10 지급. 먼저 온 10명 중 2. 버전 충돌 72~86, p95 148~153ms |
| 재고 50, 회원 50명 | **50 지급**. p95 153~214ms | **6 지급** / 충돌 44 | **26~34 지급**. 30~32건이 5번째 시도까지 갔고 그중 16~24건이 실패. 버전 충돌 163~173, p95 282~320ms |
| 재고 50, 회원 10명 × 5번 | 10 지급. 중복 거절 중 9~13건은 앱 확인이 아니라 UNIQUE | 5 지급. 버전 충돌 27~31, **데드락 1~5** | 10 지급. **데드락 4~5** |

- 세 방식 모두 사용자당 1장, 재고 이하, 지급 행 = `issued_count` 를 매 회차 지켰다.
- 비관적 락은 InnoDB 락 대기가 요청 수 - 1(49건)로 일정했다. 한 줄로 서서 하나씩 통과했다.
- 낙관적 락(재시도 없음)의 성공 건수 6 은 1단계 SERIALIZABLE(같은 조건 5~6)과 비슷했다. 동시에 열린 트랜잭션 묶음마다 한 건만 커밋에 성공한다.

**예상하지 못한 것: 낙관적 락에서 같은 회원 요청끼리 데드락**

```text
*** (1) HOLDS THE LOCK(S):
RECORD LOCKS ... index uk_coupon_issue_coupon_member of table `coupon_issues` ... lock mode S locks gap before rec
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index uk_coupon_issue_coupon_member ... lock_mode X locks gap before rec insert intention waiting
*** (2) 도 같은 모양. 두 트랜잭션 모두 insert into coupon_issues (... member_id = 957 ...)
```

같은 회원의 요청 셋 이상이 같은 (쿠폰, 회원) 키를 INSERT 할 때 생긴다. 첫 번째가 INSERT 하면 나머지는 중복 키를 만나 그 행의 S 락을 기다린다. 이때 첫 번째가 **버전 충돌로 롤백**되면, 기다리던 둘이 함께 S(갭) 락을 받는다. 그다음 둘 다 같은 자리에 INSERT 하려다 서로의 갭 락에 막힌다. MySQL 문서의 InnoDB INSERT 락 설명에 나오는 중복 키 + 롤백 데드락과 같은 모양이다. 비관적 락과 1단계 RR 에서는 첫 번째가 커밋하므로 기다리던 쪽이 `UNIQUE_VIOLATION` 을 받고 끝난다. 롤백이 잦은 방식이라서 생기는 데드락이다. 재시도는 버전 충돌만 다시 하므로 이 데드락은 그대로 실패로 남았다.

### 4-4. 재시도 조건을 바꾼 결과 (재고 50, 회원 50명, 3회)

| 재시도 설정 | 지급 | 실제로 쓰인 최대 시도 | 버전 충돌 | 서버 p95 |
|---|---|---:|---:|---|
| 최대 5회, 지연 상한 100ms (기본) | 26~34 / 50 (탐색 실행 25~29) | 5 | 163~173 | 282~320ms |
| 최대 5회, 지연 없음 | 23~24 / 50 | 5 | 172~176 | 263~307ms |
| 최대 10회 | **50 / 50** | 9~10 | 198~209 | 441~531ms |
| 최대 20회 | 50 / 50 | 10 | 200~216 | 493~639ms |

- 이 경합(요청 50건, 커넥션 10개, 한 행)에서는 시도 상한이 지급 수를 정했다. 10회면 전원 지급됐고, 20회로 올려도 실제로 쓰인 시도는 10회까지였다.
- 지연을 없애도 처리 시간이 줄지 않았고 지급 수가 조금 줄었다. 충돌한 요청들이 곧바로 다시 부딪쳤다.
- 재고보다 요청이 많은 시나리오(재고 10)는 모든 설정에서 10건이 지급됐다. 먼저 온 10명 중 당첨은 1~3명이었다.

- 처리량은 순위를 매기지 않는다. 낙관적 락의 접수 처리량이 높은 것은 충돌로 빨리 실패한 요청이 많아서다. 재고 1000 에서 실제 지급 완료 처리량은 비관적 350, 재시도 74 req/s 였다.
- 비관적 락은 재고 1000 에서 락 대기 시간 합이 24초였다(요청 999건이 한 번씩 대기). 시간 대부분이 쿠폰 행 앞 줄서기다.
- 재시도는 재고 1000 에서 요청 1000건에 트랜잭션 3974번을 썼다. 버전 충돌률은 3517 / 3974 = 약 88% 였다.
- 회원 100명 × 10번에서 재시도 없는 낙관적 락은 회원 14명이 10번 요청하고도 한 장도 받지 못했다.

선착순 관찰
- 도착 순서는 진입점 번호, 당첨은 DB 커밋 성공이다.
- 비관적 락은 HTTP 재고 100 에서 먼저 온 100명이 정확히 당첨됐고, JUnit 저장 실행도 3회 모두 10/10 이었다. 하지만 탐색 실행 한 회차에서 9/10 이 나왔다. 성공 요청끼리의 완료 순서는 HTTP 에서 10~38건이 도착 순서와 달랐다.
- 진입점에서 InnoDB 락 대기열까지 순서가 바뀔 수 있는 곳이 두 군데다. 하나는 커넥션 대기열이고, 하나는 InnoDB 의 락 부여 순서(CATS)다. 4-6 에서 각각 확인했다. 9/10 이 어느 쪽에서 생겼는지는 확인하지 못했다.
- 낙관적 락은 먼저 온 100명 중 12명만 당첨됐다. 재시도를 붙이면 46명이었다. 재시도는 실패한 요청을 뒤로 보내므로 늦게 온 요청이 먼저 성공한다.

### 4-6. 락 부여 순서: CATS (보완 실험)

**순서 고정 재현 (재고 1, 단독 4회·전체 테스트 5회 연속 같은 결과)**

별도 커넥션이 쿠폰 행을 잡은 동안 먼저 온 요청이 쿠폰 행을 기다린다. 늦게 온 요청은 회원 행을 먼저 `FOR UPDATE` 로 잠근 트랜잭션 안에서 비관적 락 지급에 들어와 쿠폰 행을 기다린다(다른 기능과 한 트랜잭션으로 묶인 지급). 그 회원 행을 기다리는 트랜잭션 수를 바꿔 가중치를 만든 뒤 쿠폰 행을 놓았다.

| 늦게 온 요청이 막고 있는 트랜잭션 | 쿠폰 행 가중치 (먼저 / 늦게) | 먼저 온 요청 | 늦게 온 요청 |
|---:|---|---|---|
| 0 | 1 / 1 | **성공** | `SOLD_OUT` |
| 3 | 1 / **4** | **`SOLD_OUT`** | 성공 |

- 가중치가 같으면 오래 기다린 쪽이 받았다. 늦게 온 쪽이 트랜잭션 3개를 막고 있으면 가중치가 4(자기 1 + 막은 3)가 되어, 먼저 기다리던 요청을 앞질러 마지막 1장을 가져갔다.
- 비관적 락으로 "줄"을 세워도 줄의 순서는 도착 순서가 아니다. 지급 트랜잭션이 쿠폰 행을 기다리기 전에 다른 락(회원, 포인트, 주문 행 등)을 쥐고 있고, 다른 트랜잭션이 그 락을 기다리면 앞지르기가 생긴다.

**이 프로젝트의 현재 흐름에서는 가중치가 같았다**
- 비관적 락은 쿠폰 행을 `FOR UPDATE` 로 얻기 전에 아무 락도 쥐지 않는다. 회원 조회는 일반 SELECT 이고, INSERT 는 쿠폰 행을 얻은 뒤에 한다. 순서 고정 기록의 쿠폰 행 대기자는 모두 가중치 1 이었다.
- HTTP 부하(2단계 k6 와 같은 조건) 중 0.2초마다 표본을 떴다. 비관적 락의 쿠폰 행 대기자는 3개 실험, 표본 269건 모두 가중치 1 이었다. 이 흐름에서 CATS 는 "오래 기다린 순서"로 동작한다.
- 같은 표본에서 한 순간에 InnoDB 에서 쿠폰 행을 기다린 트랜잭션은 최대 9개였다(커넥션 풀 10 에서 락을 쥔 1개를 뺀 수). 동시 요청 100개 중 나머지는 DB 에 닿기 전에 커넥션 대기열에서 기다렸다. 이 대기열의 순서는 CATS 와 상관없고, 이번에 따로 검증하지 않았다.
- 낙관적 락의 같은 회원 순서 고정 케이스에서는 커밋 직전 UPDATE 를 기다리는 트랜잭션의 가중치가 2 였다. INSERT 를 먼저 해 둔 행을 다른 요청이 기다렸기 때문이다. 같은 흐름에서도 락을 쥔 채 기다리면 가중치가 갈린다.

측정 중 발견한 문제
- 처음에는 먼저 온 요청을 `innodb_trx` 의 첫 쿠폰 행 대기자로 식별했는데, 전체 테스트에서 3번 중 1번 실패했다.
- 원인은 `innodb_trx` 의 0.1초 캐시였다. 직전 케이스가 끝나고 0.1초 안에 조회하면 직전 케이스의 대기 행이 보였고, 풀에서 재사용된 커넥션 id 까지 겹쳐 엉뚱한 트랜잭션을 "먼저 온 요청"으로 짚었다. 그때도 가중치 자체는 정상이었다(회원 행을 쥔 쪽 4).
- 대기 여부는 캐시가 없는 `performance_schema.data_lock_waits` 로 보고, 늦게 온 요청은 "회원 행 락을 쥔 트랜잭션"으로 식별하도록 고쳤다.

## 5. 보장하는 범위와 해결하지 못한 문제

| 기준 | 비관적 락 | 낙관적 락 | 낙관적 락 + 재시도 |
|---|---|---|---|
| 사용자당 최대 1장 | 지켜짐. 단 앱 중복 확인은 스냅샷 때문에 일부 놓치고 **UNIQUE 제약이** 막았다 | 지켜짐 (UNIQUE) | 지켜짐 (UNIQUE) |
| 지급 건수 ≤ 재고 | 지켜짐 | 지켜짐 | 지켜짐 |
| DB 지급 행 = `issued_count` | 지켜짐 | 지켜짐. **단 version 을 모르는 쓰기와 섞이면 깨짐** (4-2) | 같음 |
| 유효 요청이 충분하면 재고만큼 지급 | 지켜짐 (1000/1000) | **깨짐** (117/1000) | **깨짐** (457/1000, 5회). JUnit 50건은 10회면 지켜짐 |
| 먼저 온 요청이 당첨 | **보장 안 됨.** 현재 흐름은 가중치가 같아 대체로 지켜졌다(한 회차 9/10). 하지만 커넥션 대기열 순서는 별개이고, 다른 락을 쥔 지급이 섞이면 CATS 가 늦은 요청에 먼저 락을 준다 (4-6) | 보장 안 됨 (12/100) | 보장 안 됨 (46/100) |
| 특정 요청의 반복 실패 | 없음 | 회원 14명이 10번 모두 실패 | 5회 소진 543건, 중복 키 데드락 |

해결하지 못한 문제
- 비관적 락은 모든 요청을 쿠폰 행 하나에 줄 세운다. 실제 지급 완료 처리량은 "락을 쥔 시간" 하나로 정해진다. 기다리는 동안 커넥션도 붙잡으므로, 같은 풀을 쓰는 다른 쿠폰 요청에 주는 영향은 측정하지 않았다.
- 낙관적 락은 한 행에 경합이 몰리는 선착순 쿠폰에 맞지 않았다. 재시도로 지급 수를 채우려면 시도 수와 지연이 함께 늘어난다(10회 상한에서 p95 441~531ms).
- 버전 검사는 같은 행을 쓰는 모든 경로가 version 을 올릴 때만 의미가 있다. 이 프로젝트는 Redis 방식이 벌크 UPDATE 를 쓰므로, 같은 쿠폰에 두 방식을 섞으면 깨진다.
- 데드락은 재시도 대상에 넣지 않았다. 넣을지는 설계 선택으로 남긴다.
- DB 락으로 "선착순"을 정할 수는 없다. InnoDB 는 락을 가중치 순서로 주고, 그 앞단 커넥션 대기열도 별도의 순서를 가진다. 선착순이 요구사항이라면 순서를 정하는 지점을 따로 두고(예: 단일 진입점에서 번호 발급), 그 번호로 당첨을 판단해야 한다. 3단계 이후 Redis 지급 처리에서 다시 본다.
- 비관적 락 서비스의 중복 확인 SELECT 가 옛 스냅샷을 읽는 문제는 고치지 않았다. UNIQUE 제약이 최종 방어선이다.

## 6. 다음 단계로 넘어가는 이유

DB 락만으로 정합성과 "재고만큼 지급"을 모두 지킨 것은 비관적 락이었다. 하지만 모든 요청이 같은 행 앞에서 차례를 기다린다. 품절된 뒤에 온 900건도 X 락을 얻을 때까지 기다린 다음에야 거절됐다(HTTP 재고 100, 품절 900).

3단계에서는 중복과 수량 판단을 Redis 에서 먼저 해서 DB 까지 오는 요청을 줄인다. 이때 확인할 것:
- 현재 MULTI/EXEC 구현이 정말 "검사하고 지급 처리" 를 한 번에 하는가, Lua 와 무엇이 다른가?
- Redis 와 MySQL 이 하나의 트랜잭션이 아닐 때, 어떤 순서에서 둘의 상태가 어긋나는가?
- 이번 단계에서 본 DB 쪽 방어선(조건부 UPDATE, UNIQUE 제약)은 그중 무엇을 막는가?
