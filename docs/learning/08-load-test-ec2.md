# AWS(EC2)에서 잰 쿠폰 1장 발급 확정 한계

실행 원본 (2026-10-20): [EC2 측정](results/2026-10-20-tps-ec2.md). 인스턴스 구성과 실행 방법: [performance/ec2](../../performance/ec2/README.md)

이 문서의 숫자는 **서버가 처리할 수 있는 최대 TPS 가 아니다.** 모든 요청이 쿠폰 한 장(`coupons` 테이블의 한 행)에 몰릴 때, 그 쿠폰의 발급을 DB 에 확정할 수 있는 속도다. 한계에서도 CPU 는 MySQL 컨테이너 24~28%, 앱 인스턴스 4~6%, k6 인스턴스 2~4% 였다(3절). 꽉 찬 것은 CPU 가 아니라 **쿠폰 행의 락**이었다. 한계에서는 확정 100% 가 그 락을 기다렸고, 락은 거의 쉬지 않고 쥐어져 있었다(4절).

용어
- **따라간 최대 속도**: 두 회차 모두 목표 속도대로 확정해 낸 가장 높은 요청 속도. 조건은 Mac 측정([07 6절](07-load-test.md))과 같다: 정상 구간(측정 시작 5~28초) 확정 속도 ≥ 목표의 99%, k6 가 못 보낸 요청 0, 보내기 끝났을 때 미완료 ≤ 1%, 동기 방식은 HTTP p95 ≤ 500ms
- **확정 상한**: 요청 속도를 더 올려도 오르지 않은 확정 속도(한계를 넘은 속도에서 정상 구간에 실제로 확정된 속도). CPU 가 찼다는 뜻이 아니다

## 1. 질문과 예상

Mac 에서는 k6·앱·MySQL·Redis 가 한 기계를 나눠 쓰고 다른 프로그램도 함께 돌아, 같은 속도의 두 회차가 크게 달랐다. 세 역할을 인스턴스로 나누면
- 두 회차가 같은 값을 내는가?
- 방식별 한계와 그 순서가 Mac 과 같은가? 한계는 무엇이 정하는가?

예상: 흔들림은 줄고, 한계의 순서는 Mac 과 같다(비관적 락 < 나머지, Redis 를 쓰는 넷은 같음). 숫자는 디스크와 네트워크가 달라 Mac 과 다를 것이다.

## 2. 구성과 실행 명령

| 이름 | 유형 | 하는 일 |
|---|---|---|
| db | c7g.large (2 vCPU, 4GiB, gp3 20GiB) | 저장소 `docker-compose.yml` 의 MySQL 8.0.36·Redis 7.2. Mac 과 같은 설정과 컨테이너 제한(각 1 CPU / 1GB) |
| app | c7g.xlarge (4 vCPU, 8GiB) | 같은 jar. 발행자, Pub/Sub 구독자·Stream 소비자 프로세스 |
| k6 | c7g.large (2 vCPU, 4GiB) | 같은 k6 스크립트 |

서울 리전, 세 대 같은 서브넷, Ubuntu 24.04 (Arm). 설정마다 앱을 새로 띄우고 실험 데이터를 비운 뒤 초당 50건 30초 예열을 버리고, 각 속도 30초씩 2회.

```bash
performance/ec2/ec2.sh setup
CONFIGS=lua ROUNDS=1 RATES="200 300 400" performance/ec2/ec2.sh tps probe          # 한계 근처 찾기
WARM_RATE=50 RATES="100 120 140 160 180" PESSIMISTIC_RATES="60 80 100 120 140" performance/ec2/ec2.sh tps tps
```

## 3. 결과

50번 모두 정합성 기준이 지켜졌다. 두 회차 차이는 확정 속도로 1~4, 1초 구간 흔들림은 한계에서 ±5 안쪽이었다.

| 방식 | 따라간 최대 속도 | 확정 상한 | 한계를 넘었을 때 넘친 요청 | 한계를 넘었을 때 CPU: MySQL 컨테이너 / app / k6 |
|---|---:|---|---|---|
| 비관적 락 | 120 | 133~137 (140 req/s) | 응답 지연, p95 0.6~1.5초 | 27~28% / 5% / 3% |
| 동기 Lua | 140 | 144~145 (160·180) | 응답 지연, p95 2.1~4.3초, k6 가 못 보낸 요청 119~436건 | 25% / 5% / 3~4% |
| 비동기 | 140 | 144~147 | 응답 1ms, 보내기 끝났을 때 미완료 421~1048건 | 24~25% / 4% / 2~3% |
| Pub/Sub | 140 | 145~146 | 응답 1ms, 미완료 437~1052건 | 24~25% / 4~6% / 2~3% |
| Stream 한 스크립트 | 140 | 145~146 | 응답 1ms, 미완료 437~1059건 | 25% / 4~5% / 2~3% |

CPU 기준
- MySQL 컨테이너: 제한된 1 CPU 대비, 정상 구간(5~28초) 평균. Docker API 로 0.1초마다 기록
- app·k6: 인스턴스 전체 vCPU 대비, k6 실행 전체(준비·확인 포함) 평균. 보내는 30초만 보면 조금 더 높다
- DB 인스턴스 전체 CPU 와 Redis 컨테이너 CPU 는 기록하지 않았다

## 4. 원인: 같은 행의 락을 쥔 채 커밋 동기화를 기다린다

발급 확정 트랜잭션은 `INSERT coupon_issues` → `UPDATE coupons SET issued_count = issued_count + 1 …`(이 행의 락) → `COMMIT`(redo 로그·binlog 를 디스크에 동기화한 뒤 락을 놓음) 순서다. 같은 쿠폰을 노리는 확정은 이 락을 차례로 지나가므로, 쿠폰 한 장의 확정 속도는 1 / (락을 쥐는 시간) 을 넘지 못한다. CPU 가 남는 것과 상관없다.

**꽉 찬 것은 CPU 가 아니라 쿠폰 행의 락이었다.** 결과 API 의 `innodbLockMetricsDelta`(측정 쿠폰을 만든 뒤 InnoDB 전역 카운터 변화량)로 확정마다 행 락을 기다렸는지 봤다. 전체 표는 원본에 있다.

| 방식 | 목표 req/s | 행 락을 기다린 확정 (1회차 / 2회차) | 대기 1회 평균 |
|---|---:|---|---:|
| 동기 Lua | 120 | 6% / 4% | 3.8ms / 6.4ms |
| 동기 Lua | 140 | 59% / 31% | 2.7ms / 2.2ms |
| 동기 Lua | 160·180 | **100%** | **60ms** |
| 비동기 | 140 | 58% / 23% | 3.1ms / 2.8ms |
| 비동기 | 160·180 | **100%** | **19ms** |

- 한계 아래에서는 가끔 기다렸고, 한계를 넘자 모든 확정이 앞 확정이 락을 놓기를 기다렸다
- 기다리는 시간은 동시에 확정하려는 수로 설명된다. 동기 방식은 Hikari 커넥션 10개라 앞에 최대 9개가 서고, 비동기는 작업 스레드 4개라 앞에 3개가 선다. 60ms / 9 ≈ 19ms / 3 ≈ 6.5ms 로, 확정 한 건이 락을 쥐는 시간이 약 6.5ms 다. 1 / 6.5ms ≈ 150 이 확정 상한(약 145)과 맞는다
- 145 건 × 6.5ms ≈ 0.94 초. 1초 중 94% 이상 그 행의 락이 누군가에게 쥐어져 있었다. CPU 가 아니라 이 한 줄짜리 자원이 찬 것이다
- CPU 가 낮은 이유: 락을 기다리거나 디스크 동기화를 기다리는 동안 스레드는 잠들어 CPU 를 쓰지 않는다. MySQL 컨테이너 CPU 25% 는 초당 145 건을 실제로 처리하는 데 든 몫이다(0.25 코어 / 145 ≈ 1.7ms, 4단계에서 잰 발급 1건당 MySQL CPU 1.2~2.0ms 와 같은 범위)
- 디스크도 처리 능력이 찬 것은 아니다. 초당 145 커밋에 동기화 2~3 번씩이면 초당 수백 번으로, gp3 기본 3000 IOPS 보다 훨씬 적다. 같은 행에서는 커밋이 하나씩만 진행되므로 동기화 한 번의 지연(2.6~2.8ms)이 그대로 쌓인다. 디스크 사용량은 기록하지 않았다

**커밋 동기화 시간과 한계의 비율이 같았다.** MySQL 이 기록한 로그 파일 동기화 1회 평균(`performance_schema.file_summary_by_event_name`):

| | EC2 (EBS gp3) | Mac (Docker Desktop 가상 디스크) |
|---|---:|---:|
| redo 로그 | 2.65ms | 0.73ms |
| binlog | 2.84ms | 0.70ms |
| 커밋 1건 (`sync_binlog=1` 이라 둘 다) | 약 5.5ms | 약 1.4ms |
| Redis 를 쓰는 방식의 확정 상한 | 약 145 | 약 500~550 |

1.4 / 5.5 ≈ 0.26, 145 / 530 ≈ 0.27. 동기화만으로 계산한 상한(1 / 5.5ms ≈ 180)보다 측정값이 낮은 것은 락을 쥔 채 보내는 나머지 시간(UPDATE 뒤 COMMIT 까지의 네트워크 왕복 등)으로 본다. 나누어 재지는 않았다. Mac 의 동기화가 실제 디스크까지 내려갔는지는 확인하지 않았다.

**커밋 동기화를 끄면 한계가 145 에서 800 이상으로 올랐다.** 동기 Lua 만 `innodb_flush_log_at_trx_commit=2`·`sync_binlog=0` 으로 1회 쟀다(끝난 뒤 1/1 로 되돌림).

| 목표 req/s | 200 | 400 | 600 | 800 |
|---|---:|---:|---:|---:|
| 확정 TPS | 200 | 400 | 600 | 800 |
| HTTP p95 | 3ms | 2ms | 3ms | 4ms |
| MySQL 컨테이너 CPU | 23% | 39% | 57% | 77% |

- 그동안 커밋 88442 건에 redo 동기화 1512 회(커밋당 0.017), binlog 동기화 0 회였다
- 800 에서도 새 한계에 닿지 않았다. MySQL CPU 가 속도에 비례해 오르므로 다음 한계는 컨테이너의 1 CPU 제한일 것으로 보지만 재지 않았다

**방식 사이 차이는 Mac 보다 작았다.** 비관적 락의 확정 상한(133~137)는 동기 Lua(144~145)보다 약 7% 낮았다(Mac 에서는 약 25%). `SELECT … FOR UPDATE` 부터 락을 쥐는 만큼 더 길지만, 모두가 기다리는 커밋 동기화가 길어 그 차이가 상대적으로 작아진 것으로 본다.

**넘친 요청이 쌓이는 곳은 Mac 과 같았다.** 비동기·Pub/Sub·Stream 의 미완료는 (보낸 속도 − 확정 상한) × 30초와 맞았다(160 에서 약 420, 180 에서 약 1050). 응답은 1~2ms 그대로라 응답 시간만 보면 한계를 넘은 것을 알 수 없다. 비동기라고 확정 속도가 늘지 않는다.

## 5. 보장 범위와 해결하지 못한 문제

- 커밋 동기화를 끄는 것은 해법이 아니다. `2` 는 커밋 때 redo 를 OS 에 넘기기만 하고 약 1초마다 디스크에 동기화한다. MySQL 프로세스만 죽으면 잃지 않지만, OS 가 죽거나 전원이 나가면 이미 커밋된 마지막 약 1초를 잃을 수 있다(MySQL 설정의 의미이고 실험하지 않음). 이 프로젝트에서는 사용자가 성공 응답을 받았고 Redis 에도 예약이 있는데 DB 발급이 사라지는 상황이 된다
- 쿠폰 한 장에 모든 쓰기가 몰리는 조건만 쟀다. 쿠폰이 여러 장이면 행이 달라 락을 나눠 쓰고, 여러 커밋이 동기화 한 번을 함께 쓸 수 있어(group commit) 합계는 더 높을 것이다. 재지 않았다
- 비동기 방식의 접수(202) 한계는 재지 않았다. 180 req/s 에서도 응답 p95 1ms 였다
- EBS 유형(gp3 기본 성능)을 바꾼 경우는 보지 않았다

## 6. 다음에 볼 것

쿠폰 한 장의 확정 속도를 올리려면 같은 행의 락을 쥐는 횟수나 시간을 줄여야 한다. 후보와 각각 달라지는 보장 범위(구현하지 않음):
- 여러 건을 한 트랜잭션으로 묶어 확정: 동기화 한 번에 여러 건. DB 의 수량 검사와 내구성은 유지되지만 묶음 안 한 건의 실패 처리가 복잡해진다
- 요청마다의 `issued_count` UPDATE 제거: 수량은 Redis Lua 가 막고 DB 는 UNIQUE INSERT 만. DB 수준의 초과 발급 방어가 사라진다
- 수량을 여러 행으로 나눔: 락이 나뉜다. 합계를 맞추는 방법이 필요하다
