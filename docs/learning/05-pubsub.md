# 5단계: Redis Pub/Sub — 확정 요청을 프로세스 밖으로 보내기

실행 원본 (2026-10-19): [JUnit](results/2026-10-19-stage5-junit.md), [HTTP](results/2026-10-19-stage5-http.md)

## 1. 확인할 질문과 예상

질문
- 4단계에서는 확정 작업이 발행한 프로세스의 메모리 큐에 있어서, 그 프로세스가 죽으면 사라졌다. 작업을 Redis Pub/Sub 으로 다른 프로세스(구독자)에 보내면 무엇이 달라지는가?
- `PUBLISH` 가 성공했다는 것, 그리고 `PUBLISH` 가 돌려준 "받은 구독자 수" 는 무엇을 보장하는가?
- 구독자가 없을 때, 구독자가 중간에 멈췄다 다시 붙을 때, 받은 뒤 DB 확정이 실패할 때 메시지는 어떻게 되는가?
- 구독자가 둘이면 같은 메시지를 둘 다 받는다. 중복 처리는 DB 와 Redis 에 어떤 영향을 주는가?

실행 전 예상
- Pub/Sub 은 메시지를 저장하지 않는다. 그 순간 구독 중인 연결에만 보내므로, 구독자가 없거나 끊긴 동안 보낸 메시지는 사라지고 다시 붙어도 오지 않을 것이다.
- 받은 구독자 수가 1 이어도 구독자가 처리 전에 죽으면 사라진다. 받은 구독자 수는 완료가 아니다.
- 발행자 프로세스가 죽어도 이미 보낸 메시지는 구독자가 처리한다. 대신 유실 위치가 구독자 쪽으로 옮겨 간다.
- 구독자 2개면 모든 메시지를 두 번 처리한다. DB UNIQUE 가 두 번째를 막겠지만 보상(SREM)과 겹치면 Redis 와 DB 가 어긋날 수 있다.

## 2. 구현과 명령 실행 순서

4~6단계 공통 조건대로 3단계 Lua 예약과 같은 DB 확정·보상(`RedisIssueCouponService.confirmOrCancel`)을 쓰고, 전달 방식만 바꿨다. 확정을 실행하는 작업 스레드도 4단계와 같은 스레드 풀(`couponIssueExecutor`, 작업 스레드 4개)을 쓴다.

```
발행자 프로세스 (local 프로필, 18080)        PubSubIssueCouponService.issue()   ← 요청 스레드
  [1] RedisIssueCouponService.reserve(LUA)    EVALSHA 한 번 (3단계와 같음)
  [2] PUBLISH coupon:issue:requests "memberId:couponId"
        → 돌려받는 값: 그 순간 이 채널을 구독 중인 연결 수(받은 구독자 수). 확정 여부와 관계없다
        PUBLISH 자체가 실패하면 SREM, 요청 실패
  → HTTP 202 (PUBLISHED)

Redis: 구독 중인 연결마다 메시지를 밀어 보내고 잊는다. 저장하지 않는다

구독자 프로세스 (pubsub-consumer 프로필, 18081~)   PubSubIssueConsumer.onMessage()
  [3] 리스너 컨테이너의 구독 연결이 메시지를 받아 작업 스레드(스레드 풀 couponIssueExecutor)에 넘긴다
  [4] 작업 스레드: IssueConfirmService.confirm() (3단계와 같음), 실패하면 SREM (UNIQUE 위반 제외)
```

- **프로세스 분리**: 같은 코드에서 실행 설정(프로필)만 다르다. 구독은 `pubsub-consumer` 프로필에서만 등록되는 리스너 컨테이너(`PubSubConsumerConfig`)가 한다. 발행자 프로세스는 구독하지 않는다.
- **발행자는 확정 결과를 받지 못한다.** 그래서 결과 분류를 4단계의 `ACCEPTED` 와 나눠 `PUBLISHED` 로 기록하고, `PUBLISH` 가 돌려준 받은 구독자 수를 `publishReceivers` 로 따로 센다. 확정 여부는 DB(발급 행)와 Redis(예약만 있는 회원, `redisOnlyMembers`)를 비교해서만 알 수 있다.
- **구독자 쪽 기록**: 구독자는 처리 결과를 메모리에서 센다(`PubSubIssueConsumer.results`, SUCCESS 또는 예외 이름). 실패는 `pubsub confirm failed` 로그로 남긴다. 테스트는 앞의 것을, HTTP 실험은 뒤의 것을 본다.
- **채널은 DB 번호와 관계없다.** Redis Pub/Sub 채널은 서버 전체에서 하나라서, `SELECT` 로 나눈 db 1(테스트)과 db 2(실험 앱)가 같은 채널을 쓴다. 실험 구독자 프로세스를 띄운 채 테스트를 돌리면 테스트 메시지를 그 구독자가 받는다.
- **영속 큐나 재전송 장치는 만들지 않았다.** Pub/Sub 의 한계를 그대로 재현하는 것이 이 단계의 목적이다.

`FailurePoints` 에 `PUBSUB_BEFORE_CONFIRM`(구독자의 작업 스레드가 메시지 처리를 시작한 뒤, DB 확정 전)을 더했다.

## 3. 직접 실행할 명령과 바꿔볼 조건

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
docker compose up -d mysql redis

./gradlew test --tests '*PubSubIssueTest'
open build/lab/stage5-pubsub.md

# HTTP: 발행자와 구독자를 따로 띄운다. 같은 jar, 프로필만 다르다
./gradlew bootJar
COMMON="SPRING_DATASOURCE_URL=jdbc:mysql://localhost:3306/CouponToyProject_lab?createDatabaseIfNotExist=true SPRING_DATA_REDIS_DATABASE=2 SPRING_JPA_SHOW_SQL=false SPRING_JPA_PROPERTIES_HIBERNATE_SHOW_SQL=false"
env $COMMON SPRING_PROFILES_ACTIVE=local SERVER_PORT=18080 java -jar build/libs/CouponToyProject-0.0.1-SNAPSHOT.jar             # 발행자
env $COMMON SPRING_PROFILES_ACTIVE=pubsub-consumer SERVER_PORT=18081 java -jar build/libs/CouponToyProject-0.0.1-SNAPSHOT.jar   # 구독자

BASE_URL=http://localhost:18080 METHOD=REDIS_PUBSUB SCENARIO=burst TOTAL_COUNT=1000 \
MEMBERS=1000 VUS=100 ITERATIONS=1000 WARMUP=200 k6 run performance/k6/coupon-issue.js

docker exec coupon-toy-redis redis-cli PUBSUB NUMSUB coupon:issue:requests   # 지금 구독 중인 연결 수
```

k6 는 `REDIS_PUBSUB` 일 때 결과 API 의 `redisOnlyMembers`(Redis 에 예약만 있는 회원)가 0 이 되거나 2초 동안 줄지 않을 때까지 기다린 뒤 결과를 출력한다. 줄지 않고 멈춘 경우는 유실로 본다.

| 조건 | 바꾸는 법 | 실행 여부 |
|---|---|---|
| 구독자 수 | 구독자 프로세스(또는 테스트의 리스너 컨테이너) 0, 1, 2개 | 실행함 (4-1, 4-5, 4-7) |
| 4단계 비동기와 비교 | k6 `METHOD=REDIS_ASYNC` (같은 예약·확정을 발행자 프로세스 안의 작업 스레드가) | 실행함 (4-6) |
| 구독자 프로세스 종료 | `kill -KILL`, `kill -TERM` | 실행함 (4-8) |
| 발행자 프로세스 종료 | | 실행 안 함 |

## 4. 관찰 결과와 원인

### 4-1. 구독자가 없을 때, 그리고 다시 붙었을 때 (JUnit, 재고 1, 3번 실행 같은 결과)

| 순서 | 결과 |
|---|---|
| 구독자 0개에서 A 요청 | `PUBLISHED`(202). `PUBLISH` 가 돌려준 받은 구독자 수 **0** |
| 구독자를 붙이고, 다른 쿠폰 메시지가 처리될 때까지 기다림 | A 의 메시지는 오지 않았다. DB 발급 행 0, Redis 에만 있는 회원 1 |
| A 재요청 / B 요청 | **`DUPLICATE`** (쿠폰이 없는데 이미 발급) / `SOLD_OUT` |

Pub/Sub 은 보내는 순간 구독 중인 연결에만 전달하고 메시지를 남기지 않는다. 나중에 붙은 구독자는 지난 메시지를 받을 방법이 없다. 같은 채널은 보낸 순서대로 전달되므로, 나중에 보낸 다른 쿠폰 메시지가 처리됐다는 것은 A 의 메시지가 오는 중이 아니라는 뜻이다. 받은 구독자 수 0 은 발행 시점에 알 수 있었지만, 이 구현은 그대로 202 를 돌려줬다.

### 4-2. 정상 전달 (JUnit, 재고 1)

`PUBLISHED`, 받은 구독자 1. 구독자는 작업 스레드(`coupon-issue-async-N`)에서 확정했고(처리 결과 SUCCESS 1), DB 발급 행 1, Redis 에만 있는 회원 0. 발행자 쪽 결과 API 는 이 성공을 직접 알지 못하고 DB 와 Redis 를 비교해서만 안다.

### 4-3. 구독자가 받은 뒤 DB 확정 실패 (JUnit, 재고 1)

| 요청 | 응답 | 구독자 처리 결과 | DB 발급 행 | Redis |
|---|---|---|---:|---|
| A | `PUBLISHED`(202) | `DataAccessResourceFailureException` | 0 | 비어 있음 (구독자가 보상 SREM) |
| A 재요청 | `PUBLISHED` | SUCCESS | 1 | {A} |

4단계 4-2 와 같다. 실패는 구독자 프로세스에만 남고 A 와 발행자는 모른다.

### 4-4. 구독자가 받은 뒤 처리 전에 죽으면 (JUnit, 재고 1)

구독자의 작업 스레드가 확정 직전에 `Error` 를 던지게 했다(프로세스 종료 흉내, 보상 실행 안 됨).

| 결과 | 값 |
|---|---|
| 받은 구독자 수 | **1** |
| 구독자 처리 결과 | 없음 |
| DB 발급 행 / Redis 에만 있는 회원 | 0 / 1 |
| A 재요청 / B 요청 | `DUPLICATE` / `SOLD_OUT` |

**받은 구독자 수가 1 이어도 메시지는 사라질 수 있다.** 받은 것과 처리한 것은 다르다. 4-8 의 실제 프로세스 종료에서도 같았다.

### 4-5. 구독자 2개 (JUnit 재고 1, HTTP 재고 1000)

Pub/Sub 은 구독 중인 연결마다 같은 메시지를 보낸다. 받은 구독자 수가 2 였고, 두 구독자가 같은 확정을 모두 실행했다.

| 경우 | 구독자 처리 결과 | DB 발급 행 | Redis |
|---|---|---:|---|
| 둘 다 정상 (JUnit) | SUCCESS 1, `DataIntegrityViolationException` 1 | 1 | {A} |
| 하나가 DB 확정 실패 (JUnit) | SUCCESS 1, `DataAccessResourceFailureException` 1 | 1 | **{} — DB 에만 있는 회원 1** |
| 그 뒤 B 요청 | `CouponSoldOutAtDbException` 2 (둘 다 SREM) | 1 | {} |
| 그 뒤 A 재요청 | `DataIntegrityViolationException` 2 (UNIQUE 위반은 보상하지 않음) | 1 | {A} |

- 둘 다 정상일 때는 두 번째 처리를 DB UNIQUE 가 막아 정합성은 지켜졌다. 대신 모든 쓰기를 두 번 시도했다. HTTP 재고 1000 에서는 회차마다 UNIQUE 위반이 워밍업 포함 1200건(측정분 1000건) 났고, 두 구독자가 463~548 / 652~737 로 나눠 가졌다., 발급 완료 처리량은 구독자 1개(초당 409~447건)의 절반 수준(초당 202~254건)이었다.
- **하나가 실패하면 그 보상이 다른 구독자의 성공을 지운다.** 실패한 구독자는 "확정 실패" 로 보고 SREM 하지만, 다른 구독자는 그 롤백을 기다렸다가 같은 회원을 확정했다. 결과는 DB 에는 A 가 있고 Redis 에는 없는 상태다. 그러자 Redis 는 재고가 남았다고 보고 B 를 받았고(202), DB 조건부 UPDATE 가 막았다. B 는 202 를 받고도 쿠폰이 없다. A 가 다시 요청해야 Redis 가 A 를 다시 기록한다. 3단계 보상은 "확정을 시도한 것은 나 하나" 라는 전제였는데, 중복 전달이 그 전제를 깬다.

### 4-6. 구독자 1개 동시 요청 (JUnit 3번 실행 × 3회차, HTTP 3회)

JUnit (요청 50, 요청 스레드 50, 구독자 작업 스레드 4)

| 시나리오 | 접수 결과 | 받은 구독자 수 | 구독자 처리 결과 | 접수 뒤 처리 끝까지 ms | 먼저 온 N명 중 당첨 |
|---|---|---|---|---|---|
| 재고 10, 회원 50 | PUBLISHED 10, SOLD_OUT 40 | 1명: 10 | SUCCESS 10 | 123~139 | 5~10 / 10 |
| 재고 50, 회원 50 | PUBLISHED 50 | 1명: 50 | SUCCESS 50 | 178~372 | 50 / 50 |
| 회원 10 × 5번 | PUBLISHED 10, DUPLICATE 40 | 1명: 10 | SUCCESS 10 | 115~141 | 10 / 10 |
| 재고 50, 구독자 2개 | PUBLISHED 50 | 2명: 50 | SUCCESS 50, UNIQUE 위반 50 | 222~376 | 50 / 50 |

HTTP (발행자 18080, 구독자 18081 별도 프로세스, 같은 세션에서 4단계 비동기와 번갈아)

| 실험 | 방식 | HTTP p50 / p95 ms | 접수 req/s | 발급 완료 req/s | 확정까지 s | 마지막 응답 시점 미완료 |
|---|---|---|---|---|---|---|
| 재고 100 | 비동기 (4단계) | 13~68 / 29~119 | 1475~6211 | 129~282 | 0.35~0.78 | 6~86 / 100 |
| 재고 100 | Pub/Sub | 17~27 / 33~65 | 2825~4950 | 121~219 | 0.46~0.83 | 62~92 / 100 |
| 재고 1000 | 비동기 (4단계) | 15~25 / 45~75 | 3165~4167 | 91~252 | 3.97~11.03 | 972~980 / 1000 |
| 재고 1000 | Pub/Sub | 13~18 / 21~42 | 4608~6622 | **409~447** | 2.24~2.45 | 979~991 / 1000 |

- 정상일 때는 모든 회차에서 DB 기준 정합성이 지켜졌고, 처리가 끝난 뒤 Redis 예약 회원과 DB 발급 회원이 같았다. 구독자 실패 로그는 0건이었다.
- 재고 1000 에서 Pub/Sub 의 발급 완료 처리량이 같은 세션의 비동기보다 높았다. 확정을 맡는 작업 스레드 수(4)와 DB 확정은 같고, 다른 것은 확정이 발행자 JVM 안에서 도느냐 별도 JVM 에서 도느냐다. 다만 이 세션의 비동기는 회차마다 편차가 컸고(초당 91 → 202 → 252건) 4단계 측정(초당 334~433건)보다 낮았다. 원인은 확인하지 않았다. 4단계 4-5 에서 본 "접수가 몰리는 동안 같은 JVM 의 확정이 거의 진행되지 않는" 현상이 별도 JVM 에서는 덜했을 수 있다.
- 당첨은 3·4단계와 같이 Redis Lua 실행 순서로 정해진다.

### 4-7. 구독자 없음 (HTTP, 재고 1000)

`PUBSUB NUMSUB` 0 에서 1000명이 요청했다. 1000건 모두 `PUBLISHED`(202), 받은 구독자 0. DB 발급 0, Redis 에만 있는 회원 1000. 1000명 모두 202 를 받고 쿠폰이 없으며, 다시 요청하면 "이미 발급" 이다.

### 4-8. 구독자 프로세스 종료 (HTTP, 재고 1000, 3회씩)

[원본](results/2026-10-19-stage5-http.md). 발행이 300건을 넘으면 구독자 JVM 에 신호를 보냈다. 구독자가 끝나기 전에 1000건이 모두 발행됐다(받은 구독자 1 이 1000건).

| 신호 | 신호 → 종료 | 종료 직후 DB 발급 | Redis 에만 있는 회원 | 구독자를 다시 띄우고 3초 뒤 | 그 회원 재요청 |
|---|---|---:|---:|---|---|
| `kill -KILL` | 0.15s | 33~48 | **952~967** | 그대로 (메시지가 다시 오지 않음) | 409 "이미 쿠폰 발급 받은 사용자입니다." |
| `kill -TERM` | 3.57~4.03s | 1000 | 0 | 그대로 | - |

- SIGKILL: 구독자는 메시지를 받아 작업 스레드 풀의 큐에 쌓아 두었다가, 33~48건만 확정하고 죽었다. 나머지는 Redis 도 구독자도 갖고 있지 않으므로 다시 띄운 구독자에게 오지 않는다. 받은 구독자 수는 모두 1 이었다. 4단계 4-8 의 큐 유실이 구독자 프로세스로 옮겨 온 것이다.
- SIGTERM: 세 번 모두 큐를 다 처리하고 끝났다. 구독자의 작업 스레드는 4단계와 같은 스레드 풀이므로 종료 동작도 같고, **보장은 아니다**(4단계 4-8: 작업 스레드 1개면 큐를 버렸다).
- 처음에는 "구독자가 죽은 뒤에도 Redis 가 받은 구독자로 셌다" 고 의심했다. 따로 재 보니 SIGKILL·SIGTERM 모두 신호 후 첫 확인(0.15초)에 `PUBSUB NUMSUB` 이 0 이었고 `PUBLISH` 도 0 을 돌려줬다. 위 실험의 받은 구독자 1 은 구독자가 끝나기 전에 발행이 모두 끝났기 때문이다.

## 5. 보장하는 범위와 해결하지 못한 문제

| 기준 | @Async (4단계) | Pub/Sub (5단계) |
|---|---|---|
| 1인 1장, 재고 이하, 행 = `issued_count` | 지켜짐 | 지켜짐 (중복 전달도 DB UNIQUE 가 막음) |
| 응답이 곧 발급 완료 | 아니오 (202) | 아니오 (202) |
| 확정 결과를 아는 곳 | 발행한 프로세스(future) | 구독자 프로세스뿐. 발행자는 DB·Redis 를 비교해야 안다 |
| 처리할 쪽이 없을 때 | 해당 없음 | **사라짐** (받은 구독자 0. 발행 시점에 알 수 있지만 이 구현은 202) |
| 처리할 쪽이 받은 뒤 강제 종료 | 큐의 작업 사라짐 (865~897건) | 구독자 큐의 메시지 사라짐 (952~967건). 받은 구독자 수는 1 |
| 다시 띄우면 | 사라진 작업은 돌아오지 않음 | 사라진 메시지는 돌아오지 않음 |
| 처리할 쪽이 정상 종료 | 보장 안 됨 | 같음 (같은 스레드 풀) |
| 같은 요청을 두 번 처리 | 없음 | 구독자 수만큼. 쓰기를 두 번 시도하고, 보상과 겹치면 Redis 와 DB 가 어긋남 |
| 발행자 프로세스 강제 종료 | 해당 없음(같은 프로세스) | 재현하지 않음. 이미 PUBLISH 한 메시지는 Redis 가 구독자에게 보낸 뒤라 영향이 없을 것으로 본다 |

감지·보상할 수 있는 실패와 근거 없이 사라지는 유실
- 감지할 수 있다: 받은 구독자 0(발행 시점), `PUBLISH` 예외(발행 시점, SREM 함), 구독자의 DB 확정 실패(구독자에서, SREM 함). 받은 구독자 0 은 보상하지 않고 202 를 돌려줬다.
- 근거 없이 사라진다: 받은 구독자가 1 이상인데 구독자가 처리 전에 죽은 경우. Redis 도 구독자도 메시지를 갖고 있지 않고, 발행자는 받은 구독자 수만 봤다. 남는 것은 Redis 예약뿐이다.

해결하지 못한 문제
- Pub/Sub 은 메시지를 저장하지 않는다. 구독자가 없거나, 끊겼거나, 받고 처리 전에 죽으면 메시지는 사라지고 다시 오지 않는다.
- 받은 구독자 수는 처리 여부를 말해 주지 않는다.
- 구독자를 늘리면 처리량이 늘지 않고 같은 메시지를 중복 처리한다. 3단계 보상(SREM)은 "확정을 시도한 쪽은 하나" 라는 전제라서, 중복 처리와 섞이면 실제 발급자를 Redis 가 잊는다.
- 발행자와 사용자는 확정 결과를 모른다.

## 6. 다음 단계로 넘어가는 이유

5단계는 작업을 프로세스 밖으로 보냈지만, 보낸 메시지가 어디에도 남지 않아 받을 쪽이 없거나 받고 죽으면 사라졌다(4-1, 4-4, 4-7, 4-8). 구독자를 늘리면 나눠 처리하지 않고 같은 메시지를 중복 처리했다(4-5).

6단계 Redis Streams 는 이 세 가지를 다르게 다룬다.
- 메시지를 스트림에 저장한다. 처리할 쪽이 없어도 메시지는 남는다.
- Consumer Group 안에서는 한 메시지를 소비자 하나에게만 준다. 소비자를 늘리면 나눠 처리한다.
- 소비자가 ACK 하기 전까지 메시지는 그 소비자의 pending 목록에 남는다. 받고 죽은 소비자의 메시지를 다른 소비자가 회수(XAUTOCLAIM)할 수 있다.

그 대신 "DB 커밋 뒤 ACK 전에 죽으면 같은 메시지를 다시 처리한다" 는 새 문제가 생긴다. 다시 처리해도 결과가 같은지(UNIQUE 예외만 잡으면 `issued_count` 까지 맞는지), 그리고 Redis 예약 뒤 XADD 전에 죽는 경우를 6단계에서 재현한다.
