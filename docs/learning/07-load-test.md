# 부하 테스트: 일정한 속도로 보낼 때 어디까지 버티는가

실행 원본 (2026-10-20): [부하 테스트](results/2026-10-20-load-test.md), [따라간 최대 속도, Mac](results/2026-10-20-tps-mac.md)

## 1. 확인할 질문과 예상

1~6단계의 HTTP 측정은 k6 VU 100개가 응답을 받아야 다음 요청을 보내는 방식(burst)이었다. 서버가 느려지면 요청 속도도 함께 떨어지므로 "어느 속도부터 버티지 못하는가" 는 보이지 않는다. 이번에는 서버가 느려져도 정해진 속도로 계속 보낸다(k6 constant-arrival-rate).

질문
- 같은 쿠폰에 모든 요청이 지급되는 조건(쓰기가 가장 많은 경우)에서 방식마다 초당 몇 건까지 따라가는가?
- 따라가지 못할 때 넘친 요청은 어디에 쌓이는가? 동기 방식과 비동기 방식이 어떻게 다른가?
- 4단계에서 세운 가설(동시에 실제 지급하는 트랜잭션 수를 줄이면 처리량이 오른다)이 맞는가? 동기 Lua 에서 Hikari 커넥션을 10 → 4 로 줄여 본다.
- 요청 속도가 오르면 DB CPU 는 어떻게 되는가?

실행 전 예상
- 모든 요청이 같은 쿠폰 행을 갱신하므로 방식과 관계없이 비슷한 속도에서 한계가 온다(4단계 4-9: 행 락과 커밋 동기화가 한계, CPU 는 아님). Redis 지급 처리는 거절을 빨리 돌려줄 뿐 쓰기를 줄이지 않는다.
- 한계를 넘으면 동기 방식은 응답이 느려지고, 비동기 방식은 응답은 빠르지만 실제 지급을 기다리는 일이 쌓인다.

## 2. 조건과 실행 명령

| 항목 | 값 |
|---|---|
| 설정 | 비관적 락, 동기 Lua, 동기 Lua + Hikari 최대 4, 비동기(작업 스레드 4), Pub/Sub(구독자 프로세스 1), Stream 한 스크립트(소비자 프로세스 1, 그룹 소비자 4) |
| 속도 | 초당 150, 300, 450, 600건을 각 30초 |
| 쿠폰 | 수량 = 회원 수 = 속도 × 30. 모든 요청이 지급된다 |
| k6 | `SCENARIO=smoke`(constant-arrival-rate), VU 미리 200개, 최대 2000개, 워밍업 200건(별도 쿠폰) |
| 반복 | 설정마다 앱을 새로 띄우고 실험 데이터를 비운 뒤 150 → 600. 6개 설정을 2회 |
| 환경 | 앱·k6·Docker(MySQL 1 CPU, Redis 1 CPU)가 Mac 한 대 |

```bash
BASE_URL=http://localhost:18080 METHOD=REDIS_LUA SCENARIO=smoke RATE=450 DURATION=30s \
PRE_ALLOCATED_VUS=200 MAX_VUS=2000 MEMBERS=13500 TOTAL_COUNT=13500 WARMUP=200 CONFIRM_POLL_MS=500 \
k6 run performance/k6/coupon-issue.js

# 동기 Lua 의 Hikari 커넥션 수
SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=4 ... java -jar build/libs/CouponToyProject-0.0.1-SNAPSHOT.jar
```

## 4. 해석

**한계 속도는 방식보다 쓰기 경로가 정했다.** 같은 쿠폰에 모두 지급되는 조건에서 Redis 를 쓰는 다섯 설정은 450 req/s 까지 따라갔고, 600 req/s 에서는 초당 463~585건에서 멈췄다(비동기 2회차 463 을 빼면 524~585). 비관적 락은 그보다 낮은 초당 375~400건이 한계였다.
- 모든 실제 지급이 같은 쿠폰 행을 UPDATE 하고 커밋한다. 4단계 4-9 에서 COMMIT 1건은 1.5~2.5ms 였고(대부분 디스크 동기화 대기), 같은 행을 갱신하는 트랜잭션은 그 행 락을 잡은 채 커밋까지 기다리므로 차례로 지나간다. 1 / 1.8ms ≈ 초당 550건으로, 측정한 한계와 맞는다. 다만 이 계산은 측정값에 맞춘 설명이고 따로 증명하지 않았다.
- 비관적 락은 같은 행 락을 `SELECT … FOR UPDATE` 부터 잡아, 중복 확인 SELECT, INSERT, UPDATE, COMMIT 까지 쥔다. 락을 쥐는 시간이 길어 한계가 낮다.
- Redis 지급 처리는 이 조건에서 한계를 올리지 않는다. 모든 요청이 결국 DB 에 써야 하기 때문이다. Redis 가 효과를 내는 것은 거절이 많은 경우다(3단계 4-7: 재고 100 에 요청 1000).

**넘친 요청이 쌓이는 곳이 달랐다.**
- 동기 방식(비관적 락, 동기 Lua): 응답이 느려졌다(p95 0.5~5.5초). k6 VU 2000개가 모두 응답을 기다려 목표 속도대로 보내지 못한 요청이 생겼다(129~4620건). 실제 서비스라면 사용자가 기다리거나, 그 앞의 연결 대기열에 쌓인다.
- 비동기 방식(비동기, Pub/Sub, Stream): 응답은 2~3ms 그대로였다. 대신 보내기를 마쳤을 때 실제 지급을 기다리는 일이 565~4066건 쌓여 있었다. 비동기는 작업 스레드 풀의 메모리 큐, Pub/Sub 은 구독자 프로세스의 메모리 큐, Stream 은 Redis 스트림에 쌓였다. 쌓인 곳에 따라 그 사이 프로세스가 죽었을 때 사라지는지가 갈린다(4단계 4-8, 5단계 4-8, 6단계 4-11).
- 비동기라고 처리량이 늘지는 않았다. 600 req/s 에서 실제 지급 완료 처리량은 동기 Lua 와 같은 범위였다. 응답 시간과 실제 지급을 기다리는 일의 양을 바꿨을 뿐이다.

**Hikari 커넥션 10 → 4 는 차이가 없었다.** 450·600 req/s 모두 범위가 겹쳤다. 4단계에서 burst(1000건을 한꺼번에) 측정으로 세운 가설(동시에 실제 지급하는 수를 줄이면 처리량이 오른다)은 이 일정 속도 측정에서는 확인되지 않았다. burst 는 짧은 순간 수백 건이 같은 행에 몰려 락 대기가 크게 쌓이지만, 일정 속도에서는 몰리는 정도가 덜했던 것으로 본다(따로 확인하지 않음).

**DB CPU 는 속도에 비례해 오르다가 한계 속도에서 60% 에 멈췄다.** 150 req/s 에서 19~30%, 300 에서 31~41%, 450 에서 42~55%, 600 에서 59~60% 였다(1코어 = 100%). 한계 속도에서도 CPU 는 차지 않았다. 4단계 4-9 와 같이 막은 것은 CPU 가 아니라 같은 행의 락과 커밋 동기화다. Stream 은 450 req/s 에서 다른 설정보다 CPU 가 10% 남짓 높았는데, 소비자가 읽을 때마다 Redis 연결을 새로 맺는 것(6단계 4-14)과의 관계는 확인하지 않았다(측정한 것은 MySQL 컨테이너 CPU 다).

## 5. 이 측정의 한계와 남은 것

- 앱, k6, MySQL, Redis 가 Mac 한 대에서 CPU 를 나눠 썼다. 600 req/s 에서는 k6 자체도 CPU 를 쓴다. 부하 발생기를 다른 기계로 옮기면 숫자가 달라질 수 있다.
- 30초씩 2회다. 오래 돌렸을 때(메모리 큐나 스트림이 계속 쌓일 때)의 모습은 보지 않았다.
- 쿠폰 하나에 모든 쓰기가 몰리는 조건만 쟀다. 쿠폰이 여러 개면 행 락이 나뉘어 한계가 오르고, 그때는 DB CPU 가 먼저 찰 수 있다.
- 거절이 많은 조건(재고보다 훨씬 많은 요청)은 일정 속도로 재지 않았다.
- 600 req/s 를 넘는 속도와, k6 VU 상한(2000)에 따른 영향은 보지 않았다.

## 6. 쿠폰 1장의 따라간 최대 속도 (Mac): 다섯 방식 중 셋은 정하지 못함

실행 원본 (2026-10-20): [따라간 최대 속도, Mac](results/2026-10-20-tps-mac.md)

450~700 req/s 를 50 단위로 2회씩 재고, "두 회차 모두 목표 속도의 99% 를 지급하고, 못 보낸 요청이 없고, 미완료가 1% 이하이고, 동기 방식은 p95 500ms 이하" 인 가장 높은 속도(따라간 최대 속도)를 구하려 했다. 서버의 최대 TPS 가 아니라, 모든 요청이 쿠폰 한 장에 몰릴 때 그 쿠폰을 DB 에 실제로 지급해 낸 속도다.

결과: 이 조건을 두 회차 모두 만족한 가장 높은 속도는 비관적 락 300, 비동기 500 이었다. 동기 Lua·Pub/Sub·Stream 은 같은 속도의 두 회차가 크게 달라 정하지 못했다.
- 동기 Lua 450: 1회차 464 TPS(p95 813ms) / 2회차 351 TPS(p95 5.6초). 그런데 500 은 두 회차 모두 495~498 TPS(p95 281~354ms)였다. 속도를 올렸는데 결과가 좋아지는, 측정 순서와 상관없는 흔들림이다
- Stream 450: 1회차 117 TPS / 2회차 409 TPS. 600 은 397 / 85 TPS
- 처음 요약은 정상 구간을 5~30초로 잡아 약 1% 낮게 계산했다(30초가 보내기가 끝나는 시점이라 1초 표본 사이 보간이 멈춘 뒤 값과 섞임). 5~28초로 고쳐 다시 계산했고, 그 전에는 비관적 락 300 과 비동기 500 도 조건 미달로 나왔다

조건을 떠나 범위로만 보면 앞선 측정(3~4절)과 같은 모습이다. 비관적 락은 350~400, 동기 Lua·비동기·Pub/Sub 은 500 안팎에서 더 오르지 않았다. 비동기·Pub/Sub·Stream 은 그 위에서 응답은 2~5ms 그대로이고 미완료가 쌓였다.

측정 중 Mac 은 다른 프로그램(`fseventsd` CPU 약 100%, 스왑 약 10GB)이 함께 돌고 있었다. 이 상태에서는 50 단위 차이를 가를 수 없어서, 앱·DB·k6 를 따로 둔 EC2 에서 다시 잰다.

남은 문제: 앱을 띄운 직후 첫 부하에서 지연이 크다(원본의 "예열" 참고). JVM 웜업으로 줄일 수 있을 것으로 보지만 원인을 나누어 확인하지 않았다.
