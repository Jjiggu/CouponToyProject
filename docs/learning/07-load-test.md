# 부하 테스트: 일정한 속도로 보낼 때 어디까지 버티는가

실행 원본 (2026-10-20): [부하 테스트](results/2026-10-20-load-test.md), [최대 발급 TPS, Mac](results/2026-10-20-tps-mac.md), [최대 발급 TPS, EC2](results/2026-10-20-tps-ec2.md)

## 1. 확인할 질문과 예상

1~6단계의 HTTP 측정은 k6 VU 100개가 응답을 받아야 다음 요청을 보내는 방식(burst)이었다. 서버가 느려지면 요청 속도도 함께 떨어지므로 "어느 속도부터 버티지 못하는가" 는 보이지 않는다. 이번에는 서버가 느려져도 정해진 속도로 계속 보낸다(k6 constant-arrival-rate).

질문
- 같은 쿠폰에 모든 요청이 발급되는 조건(쓰기가 가장 많은 경우)에서 방식마다 초당 몇 건까지 따라가는가?
- 따라가지 못할 때 넘친 요청은 어디에 쌓이는가? 동기 방식과 비동기 방식이 어떻게 다른가?
- 4단계에서 세운 가설(동시에 확정하는 트랜잭션 수를 줄이면 처리량이 오른다)이 맞는가? 동기 Lua 에서 Hikari 커넥션을 10 → 4 로 줄여 본다.
- 요청 속도가 오르면 DB CPU 는 어떻게 되는가?

실행 전 예상
- 모든 요청이 같은 쿠폰 행을 갱신하므로 방식과 관계없이 비슷한 속도에서 한계가 온다(4단계 4-9: 행 락과 커밋 동기화가 한계, CPU 는 아님). Redis 예약은 거절을 빨리 돌려줄 뿐 쓰기를 줄이지 않는다.
- 한계를 넘으면 동기 방식은 응답이 느려지고, 비동기 방식은 응답은 빠르지만 확정을 기다리는 일이 쌓인다.

## 4. 해석

**한계 속도는 방식보다 쓰기 경로가 정했다.** 같은 쿠폰에 모두 발급되는 조건에서 Redis 를 쓰는 다섯 설정은 450 req/s 까지 따라갔고, 600 req/s 에서는 초당 463~585건에서 멈췄다(비동기 2회차 463 을 빼면 524~585). 비관적 락은 그보다 낮은 초당 375~400건이 한계였다.
- 모든 확정이 같은 쿠폰 행을 UPDATE 하고 커밋한다. 4단계 4-9 에서 COMMIT 1건은 1.5~2.5ms 였고(대부분 디스크 동기화 대기), 같은 행을 갱신하는 트랜잭션은 그 행 락을 잡은 채 커밋까지 기다리므로 차례로 지나간다. 1 / 1.8ms ≈ 초당 550건으로, 측정한 한계와 맞는다. 다만 이 계산은 측정값에 맞춘 설명이고 따로 증명하지 않았다.
- 비관적 락은 같은 행 락을 `SELECT … FOR UPDATE` 부터 잡아, 중복 확인 SELECT, INSERT, UPDATE, COMMIT 까지 쥔다. 락을 쥐는 시간이 길어 한계가 낮다.
- Redis 예약은 이 조건에서 한계를 올리지 않는다. 모든 요청이 결국 DB 에 써야 하기 때문이다. Redis 가 효과를 내는 것은 거절이 많은 경우다(3단계 4-7: 재고 100 에 요청 1000).

**넘친 요청이 쌓이는 곳이 달랐다.**
- 동기 방식(비관적 락, 동기 Lua): 응답이 느려졌다(p95 0.5~5.5초). k6 VU 2000개가 모두 응답을 기다려 목표 속도대로 보내지 못한 요청이 생겼다(129~4620건). 실제 서비스라면 사용자가 기다리거나, 그 앞의 연결 대기열에 쌓인다.
- 비동기 방식(비동기, Pub/Sub, Stream): 응답은 2~3ms 그대로였다. 대신 보내기를 마쳤을 때 확정을 기다리는 일이 565~4066건 쌓여 있었다. 비동기는 작업 스레드 풀의 메모리 큐, Pub/Sub 은 구독자 프로세스의 메모리 큐, Stream 은 Redis 스트림에 쌓였다. 쌓인 곳에 따라 그 사이 프로세스가 죽었을 때 사라지는지가 갈린다(4단계 4-8, 5단계 4-8, 6단계 4-11).
- 비동기라고 처리량이 늘지는 않았다. 600 req/s 에서 발급 완료 처리량은 동기 Lua 와 같은 범위였다. 응답 시간과 확정을 기다리는 일의 양을 바꿨을 뿐이다.

**Hikari 커넥션 10 → 4 는 차이가 없었다.** 450·600 req/s 모두 범위가 겹쳤다. 4단계에서 burst(1000건을 한꺼번에) 측정으로 세운 가설(동시에 확정하는 수를 줄이면 처리량이 오른다)은 이 일정 속도 측정에서는 확인되지 않았다. burst 는 짧은 순간 수백 건이 같은 행에 몰려 락 대기가 크게 쌓이지만, 일정 속도에서는 몰리는 정도가 덜했던 것으로 본다(따로 확인하지 않음).

**DB CPU 는 속도에 비례해 오르다가 한계 속도에서 60% 에 멈췄다.** 150 req/s 에서 19~30%, 300 에서 31~41%, 450 에서 42~55%, 600 에서 59~60% 였다(1코어 = 100%). 한계 속도에서도 CPU 는 차지 않았다. 4단계 4-9 와 같이 막은 것은 CPU 가 아니라 같은 행의 락과 커밋 동기화다. Stream 은 450 req/s 에서 다른 설정보다 CPU 가 10% 남짓 높았는데, 소비자가 읽을 때마다 Redis 연결을 새로 맺는 것(6단계 4-14)과의 관계는 확인하지 않았다(측정한 것은 MySQL 컨테이너 CPU 다).

## 5. 이 측정의 한계와 남은 것

- 앱, k6, MySQL, Redis 가 Mac 한 대에서 CPU 를 나눠 썼다. 600 req/s 에서는 k6 자체도 CPU 를 쓴다. 부하 발생기를 다른 기계로 옮기면 숫자가 달라질 수 있다.
- 30초씩 2회다. 오래 돌렸을 때(메모리 큐나 스트림이 계속 쌓일 때)의 모습은 보지 않았다.
- 쿠폰 하나에 모든 쓰기가 몰리는 조건만 쟀다. 쿠폰이 여러 개면 행 락이 나뉘어 한계가 오르고, 그때는 DB CPU 가 먼저 찰 수 있다.
- 거절이 많은 조건(재고보다 훨씬 많은 요청)은 일정 속도로 재지 않았다.
- 600 req/s 를 넘는 속도와, k6 VU 상한(2000)에 따른 영향은 보지 않았다.

## 6. 최대 발급 TPS 측정 (Mac): 다섯 방식 중 셋은 정하지 못함

실행 원본 (2026-10-20): [최대 발급 TPS, Mac](results/2026-10-20-tps-mac.md)

450~700 req/s 를 50 단위로 2회씩 재고, "두 회차 모두 목표 속도의 99% 를 발급하고, 못 보낸 요청이 없고, 미완료가 1% 이하이고, 동기 방식은 p95 500ms 이하" 인 가장 높은 속도를 최대 발급 TPS 로 보려 했다.

결과: 이 조건을 두 회차 모두 만족한 가장 높은 속도는 비관적 락 300, 비동기 500 이었다. 동기 Lua·Pub/Sub·Stream 은 같은 속도의 두 회차가 크게 달라 정하지 못했다.
- 동기 Lua 450: 1회차 464 TPS(p95 813ms) / 2회차 351 TPS(p95 5.6초). 그런데 500 은 두 회차 모두 495~498 TPS(p95 281~354ms)였다. 속도를 올렸는데 결과가 좋아지는, 측정 순서와 상관없는 흔들림이다
- Stream 450: 1회차 117 TPS / 2회차 409 TPS. 600 은 397 / 85 TPS
- 처음 요약은 정상 구간을 5~30초로 잡아 약 1% 낮게 계산했다(30초가 보내기가 끝나는 시점이라 1초 표본 사이 보간이 멈춘 뒤 값과 섞임). 5~28초로 고쳐 다시 계산했고, 그 전에는 비관적 락 300 과 비동기 500 도 조건 미달로 나왔다

조건을 떠나 범위로만 보면 앞선 측정(3~4절)과 같은 모습이다. 비관적 락은 350~400, 동기 Lua·비동기·Pub/Sub 은 500 안팎에서 더 오르지 않았다. 비동기·Pub/Sub·Stream 은 그 위에서 응답은 2~5ms 그대로이고 미완료가 쌓였다.

측정 중 Mac 은 다른 프로그램(`fseventsd` CPU 약 100%, 스왑 약 10GB)이 함께 돌고 있었다. 이 상태에서는 50 단위 차이를 가를 수 없어서, 앱·DB·k6 를 따로 둔 EC2 에서 다시 잰다.

남은 문제: 앱을 띄운 직후 첫 부하에서 지연이 크다(원본의 "예열" 참고). JVM 웜업으로 줄일 수 있을 것으로 보지만 원인을 나누어 확인하지 않았다.

## 7. 최대 발급 TPS 측정 (EC2): 앱·DB·k6 를 나눠서

실행 원본 (2026-10-20): [최대 발급 TPS, EC2](results/2026-10-20-tps-ec2.md). 준비와 실행 방법: [performance/ec2](../../performance/ec2/README.md)

조건: 서울 리전 같은 서브넷에 db(c7g.large, MySQL·Redis 컨테이너는 Mac 과 같은 설정과 1 CPU / 1GB 제한), app(c7g.xlarge), k6(c7g.large). 같은 jar, 같은 k6 스크립트, 같은 판정. 예열은 초당 50건(한계 아래), 각 속도 30초, 2회.

| 방식 | 최대 발급 TPS (두 회차 모두 조건 충족) | 다음 속도에서 발급 TPS | 다음 속도에서 넘친 요청 |
|---|---:|---|---|
| 비관적 락 | 120 | 140 → 133~137 | 응답 지연 (p95 0.6~1.5초) |
| 동기 Lua | 140 | 160 → 144~145 | 응답 지연 (p95 2.1~2.2초), k6 가 못 보낸 요청 119~133건 |
| 비동기 | 140 | 160 → 146 | 응답은 1ms, 보내기 끝났을 때 미완료 421~426건 |
| Pub/Sub | 140 | 160 → 145~146 | 응답은 1ms, 미완료 437~438건 |
| Stream 한 스크립트 | 140 | 160 → 145~146 | 응답은 1ms, 미완료 437~450건 |

50건 모두 정합성 기준이 지켜졌다. 두 회차 차이는 발급 TPS 로 1~4, 1초 구간 흔들림도 한계에서 ±5 안쪽이었다. 그 사이 app 인스턴스 CPU 4~16%, k6 인스턴스 2~4%, MySQL 컨테이너 11~28% 로, 셋 다 한계가 아니었다.

**한계는 Mac 의 약 4분의 1 이었고, 그 비율은 커밋 동기화 시간의 비율과 같았다.**
- Redis 를 쓰는 네 방식의 한계는 144~147 TPS 로 같았다(Mac 500~550). 모두 같은 쿠폰 행을 UPDATE 하고 커밋하는 같은 DB 확정을 지나가기 때문이다
- MySQL 이 기록한 로그 파일 동기화 1회 평균은 EC2(EBS gp3) redo 2.65ms·binlog 2.84ms, Mac(Docker Desktop 가상 디스크) 0.73ms·0.70ms 였다. `sync_binlog=1` 이라 커밋마다 둘 다 기다리므로 커밋 1건에 약 5.5ms 대 1.4ms. 비율 0.26 이 한계 TPS 비율(145 / 530 ≈ 0.27)과 맞는다. 같은 행의 락을 쥔 채 커밋 동기화를 기다리므로 한 쿠폰의 발급 TPS 는 커밋 동기화 시간에 묶인다
- 커밋 동기화만으로 계산한 상한(1 / 5.5ms ≈ 180)보다 측정한 한계(145)가 낮은 것은 락을 쥔 채 보내는 나머지 시간(UPDATE 뒤 COMMIT 까지의 네트워크 왕복 등)으로 본다. 나누어 재지는 않았다
- Mac 의 디스크 동기화가 실제 디스크까지 내려갔는지는 확인하지 않았다. Mac 에서 잰 TPS 는 그 환경에서만 의미가 있다

**방식 사이 차이는 Mac 보다 작았다.** 비관적 락의 한계(133~137)는 동기 Lua(144~145)보다 약 7% 낮았다(Mac 에서는 약 25%). `SELECT … FOR UPDATE` 부터 락을 쥐는 만큼 더 길지만, EC2 에서는 모두가 기다리는 커밋 동기화가 길어 그 차이가 상대적으로 작아진 것으로 본다.

**넘친 요청이 쌓이는 곳은 Mac 과 같았고 더 깨끗하게 보였다.** 비동기·Pub/Sub·Stream 의 미완료는 (보낸 속도 − 한계) × 30초와 맞았다. 160 에서 (160 − 146) × 30 ≈ 420, 180 에서 (180 − 145) × 30 ≈ 1050 이었다. 세 방식 모두 응답은 1~2ms 그대로라 응답 시간만 보면 한계를 넘은 것을 알 수 없다. 쌓이는 곳(작업 스레드 큐, 구독자 프로세스 메모리, Redis 스트림)이 다를 뿐이고, 그 차이는 프로세스가 죽었을 때 드러난다(4~6단계).

**커밋 동기화를 끄면 한계가 145 에서 800 이상으로 올랐다.** 동기 Lua 만, `innodb_flush_log_at_trx_commit=2`·`sync_binlog=0` 으로 바꿔 1회 쟀다(끝난 뒤 1/1 로 되돌림).
- 200·300·400·500·600·800 req/s 모두 목표 속도대로 발급했고 p95 2~4ms 였다(동기화를 켰을 때는 낮은 속도에서도 p95 10~15ms). 800 에서 MySQL CPU 77% 로, 이번 범위에서는 새 한계에 닿지 않았다. 다음 한계는 컨테이너의 1 CPU 제한일 것으로 보지만 재지 않았다
- 그동안 커밋 88442 건에 redo 동기화 1512 회(커밋당 0.017), binlog 동기화 0 회였다. 설정이 커밋마다의 동기화를 실제로 없앴다
- 이 설정의 대가(MySQL 설정의 의미이고 실험하지 않음): `2` 는 커밋 때 redo 를 OS 에 넘기기만 하고 약 1초마다 디스크에 동기화한다. MySQL 프로세스만 죽으면 잃지 않지만, OS 가 죽거나 전원이 나가면 이미 커밋된 마지막 약 1초를 잃을 수 있다. `sync_binlog=0` 이면 binlog 도 OS 에 맡긴다. 이 프로젝트에서는 사용자가 성공 응답을 받았고 Redis 에도 예약이 있는데 DB 발급이 사라지는 상황이 된다. "성공이라고 답한 발급은 남아야 한다" 는 조건과 맞지 않으므로, 처리량을 올리려면 같은 행에 쓰기가 몰리지 않게 하는 쪽을 먼저 봐야 한다

남은 것
- 쿠폰 하나에 모든 쓰기가 몰리는 조건만 쟀다. 같은 행에 몰리지 않게 나누는 방법(예: 수량을 여러 행으로 나눔)은 비교하지 않았다
- EBS 유형(gp3 기본 성능)을 바꾼 경우, 동기화를 끈 상태의 새 한계는 보지 않았다
