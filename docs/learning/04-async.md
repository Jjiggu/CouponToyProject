# 4단계: Spring @Async — 접수와 DB 확정 나누기

실행 원본 (2026-10-19): [JUnit](results/2026-10-19-stage4-junit.md), [k6](results/2026-10-19-stage4-k6.md), [실제 프로세스 종료](results/2026-10-19-stage4-kill.md)

## 1. 확인할 질문과 예상

질문
- 기존 이벤트 방식(`publishEvent` → `@TransactionalEventListener` → `@Async`)은 실제로 어느 스레드, 어느 트랜잭션에서, 언제 실행되는가?
- 202 를 받은 요청의 DB 확정은 언제 끝나는가? 접수와 완료 사이에는 무엇이 남는가?
- 스레드 풀 크기, 큐 용량, 거부 정책은 무엇이고, 큐가 가득 차면 요청은 어떻게 되는가?
- 확정 작업이 실패하거나 프로세스가 죽으면 작업은 어디서 실행되고 어디서 사라지는가?

실행 전 예상
- 응답은 빨라지지만, 발급 완료 처리량은 3단계 동기 Lua 와 비슷할 것이다. 같은 DB 확정이 같은 쿠폰 행 앞에 줄을 서기 때문이다.
- 큐는 JVM 메모리에 있다. 프로세스가 죽으면 큐에 있던 작업이 사라지고 Redis 예약만 남을 것이다.
- 확정 실패는 이미 202 를 받은 사용자에게 전달되지 않을 것이다.

## 2. 기존 구현 확인과 재작성

### 기존 구현 (재작성 전)

| | 커밋된 코드 (HEAD) | 작업 전부터 있던 미커밋 변경 |
|---|---|---|
| 요청 경로 | `@Transactional` 메서드 안에서 MULTI/EXEC 예약(`checkAndRegister`) → `publishEvent` | 같은 흐름, `@Transactional` 제거 |
| 리스너 | `@Async` + `@Transactional(REQUIRES_NEW)` + `@TransactionalEventListener(AFTER_COMMIT)` | `@Async` + `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution = true)`, 안에서 `TransactionTemplate(REQUIRES_NEW)` |
| DB 확정 | 회원·쿠폰 SELECT → INSERT → 조건부 UPDATE (리스너가 직접) | 회원·쿠폰 SELECT → 조건부 UPDATE → INSERT |
| 확정 실패 시 | 예외를 잡아 로그, SREM | 예외를 잡아 로그. SREM 없음 |
| 스레드 풀 | `couponIssueEventExecutor`: core 4, max 8, 큐 50000, 거부 정책 지정 없음(Abort) | 같음 |

미커밋 변경 상태 그대로 그 변경에 들어 있던 테스트(`EventIssueCouponServiceTest`, 재고 20 에 80명 동시, 회원 20명 × 4번) 2개를 실행했고 둘 다 통과했다. 정상 경로는 동작했다. 이 파일들은 재작성 전에 `git stash` 로 보관했다(`stash@{0}`. 보는 법은 [학습 README 의 삭제 표](README.md#삭제-2026-10-19)).

`@TransactionalEventListener` 가 트랜잭션 유무에 따라 어떻게 도는지는 `TransactionalEventListenerTest` 로 확인했다(리스너 3개를 같은 이벤트에 걸고 실행 스레드와 그 스레드의 트랜잭션 여부를 기록).

| 발행한 곳 | `AFTER_COMMIT` (기본) | `fallbackExecution = true` | `@Async` + `fallbackExecution = true` |
|---|---|---|---|
| 트랜잭션 밖 | **실행되지 않는다. 예외도 INFO 로그도 없다** | 발행 즉시, 발행한 스레드에서 | 풀 스레드에서, 트랜잭션 없음 |
| 트랜잭션 안, 커밋 | 커밋 뒤, 발행한 스레드에서. 이때 그 스레드는 아직 트랜잭션 동기화 중(`isActualTransactionActive()` true) | 같음 | 커밋 뒤 풀로 넘겨짐, 풀 스레드에는 트랜잭션 없음 |
| 트랜잭션 안, 롤백 | 실행되지 않음 | 실행되지 않음 | 풀로 넘겨지지도 않음 |

이것으로 본 기존 구현의 문제
- 발급 요청 경로에는 DB 트랜잭션이 없다(Redis 예약뿐). HEAD 는 이벤트를 발화시키려고 Redis 만 쓰는 메서드에 `@Transactional` 을 붙였다. 아무 DB 작업 없이 커넥션만 잡았다 놓는다. 이 애너테이션을 지우면 리스너는 **조용히 실행되지 않는다**. 미커밋 변경은 지우면서 `fallbackExecution = true` 를 붙였는데, 그러면 "커밋 뒤" 라는 조건이 지킬 대상 없이 바로 실행된다. 어느 쪽이든 트랜잭션 이벤트를 쓸 이유가 없다.
- `AFTER_COMMIT` 리스너가 도는 순간에도 트랜잭션 동기화가 살아 있다. Spring 문서(`TransactionSynchronization.afterCommit`)에 따르면 거기서 DB 를 쓰면 이미 커밋된 트랜잭션에 참여하고 다시 커밋되지 않는다(실행하지 않음). 그래서 HEAD 는 리스너에 `REQUIRES_NEW` 를 붙였다. Spring 6.1 에 들어온 `RestrictedTransactionalEventListenerFactory` 는 `REQUIRES_NEW`·`NOT_SUPPORTED` 가 아닌 `@Transactional` 을 `@TransactionalEventListener` 에 붙이지 못하게 막는다.

| 기존 | 문제 | 바꾼 것 |
|---|---|---|
| MULTI/EXEC 예약 `checkAndRegister` | 3단계에서 본 SREM 전 틈(거짓 품절, 영구 잔여 예약) | 4~6단계 공통 기준인 Lua 예약 (`RedisIssueCouponService.reserve`) |
| 리스너가 DB 확정을 따로 구현 | 3단계 `IssueConfirmService` 와 다른 확정 로직이라 비교 조건이 달라진다 | `IssueConfirmService.confirm()` 과 보상(SREM)을 3단계 코드 그대로 (`confirmOrCancel`) |
| HEAD: `try/catch` 가 `@Transactional(REQUIRES_NEW)` 메서드 안 | 예외를 삼키면 트랜잭션이 롤백되지 않고 커밋된다. INSERT 뒤 UPDATE 가 0건(품절)이면 발급 행만 커밋되어 행 수 ≠ `issued_count` (코드로 확인, 실행하지 않음) | 확정 트랜잭션은 별도 빈, 실패는 예외 그대로 future 에 담는다 |
| HEAD: 모든 실패에 SREM / 미커밋: SREM 없음 | UNIQUE 위반에도 SREM 하면 실제 발급자를 잊는다(3단계). SREM 이 없으면 확정에 실패한 회원이 계속 "이미 발급" | 3단계와 같이 UNIQUE 위반만 남기고 나머지 실패는 SREM |
| 실패를 로그로만 남김 | 202 를 받은 요청의 최종 결과를 셀 수 없다 | `@Async` 메서드가 `CompletableFuture` 를 돌려준다. 결과 API 에 `asyncResults`(확정 결과), `pending`(아직 결과 없음), `confirmLatencyMs`(진입 → 커밋) |
| core 4, max 8, 큐 50000 | `ThreadPoolExecutor` 는 큐가 가득 찬 뒤에야 core 를 넘겨 스레드를 늘린다. 50000건이 쌓이기 전에는 늘 4개다 | `pool-size` 하나 (core = max) |
| 이벤트 객체 + 리스너 + 메트릭 | 같은 프로세스 안에서 메서드 하나를 다른 스레드로 넘기는 데 간접 단계가 셋 | `@Async` 메서드 하나(`confirmLater`). `CouponIssuedEvent`, `CouponIssueEventListener`, `CouponIssueMetrics`, `CouponIssueResult` 삭제 |
| 메트릭(`coupon_issue_*`) | 이벤트 방식에서만 기록됐고, Grafana 패널 4개만 썼다 | 결과 API 로 대체. 패널 4개 삭제 |
| `REDIS_EVENT` | 이벤트를 쓰지 않으므로 이름이 맞지 않는다 | `REDIS_ASYNC`, 서비스 이름 `AsyncIssueCouponService` |

### 재작성한 구현

```
AsyncIssueCouponService.issue()                       ← 요청 스레드 (Tomcat)
  [1] RedisIssueCouponService.reserve(LUA)             EVALSHA 한 번 (3단계와 같음)
  [2] RedisIssueCouponService.confirmLater()  @Async  작업을 couponIssueExecutor 큐에 넣고 바로 반환
        큐가 가득 차면: 요청 스레드에서 TaskRejectedException → SREM → HTTP 503
  → HTTP 202 (접수)

couponIssueExecutor 스레드
  [3] IssueConfirmService.confirm()                   새 DB 트랜잭션: INSERT, 조건부 UPDATE, COMMIT (3단계와 같음)
  [4] 실패하면 SREM (UNIQUE 위반 제외)                   3단계와 같음
  → CompletableFuture 완료 → LabService 가 확정 결과와 진입 → 커밋 시간을 기록
```

- `@Async` 는 프록시가 가로챌 때만 동작한다. `confirmLater` 는 다른 빈(`AsyncIssueCouponService`)이 불러야 한다. 같은 클래스 안에서 부르면 프록시를 지나지 않아 요청 스레드에서 동기로 돈다(이번에 실행하지 않음).
- 풀 스레드에는 요청 스레드의 트랜잭션이 없다(4-1 에서 확인). 확정 트랜잭션은 `IssueConfirmService` 의 `@Transactional` 이 풀 스레드에서 새로 연다.
- `void` 를 돌려주는 `@Async` 메서드라면 작업 예외는 `AsyncUncaughtExceptionHandler`(기본은 로그) 로만 간다. 호출한 쪽은 결과를 알 수 없다. 그래서 `CompletableFuture` 를 돌려준다.

스레드 풀 (`AsyncConfig.couponIssueExecutor`)

| 항목 | 값 | 바꾸는 법 |
|---|---|---|
| 스레드 | 4개 고정 (core = max) | `COUPON_ISSUE_ASYNC_POOL_SIZE` |
| 큐 | 50000 (`LinkedBlockingQueue`, JVM 메모리) | `COUPON_ISSUE_ASYNC_QUEUE_CAPACITY` |
| 거부 정책 | `AbortPolicy`(기본값). 작업을 넣으려던 요청 스레드에서 `TaskRejectedException` | 코드 |
| 종료 | `waitForTasksToCompleteOnShutdown=false`(기본값). 4-8 참고 | 코드 |

## 4. 관찰 결과와 원인

### 4-1. 접수와 확정 사이 (JUnit, 재고 1, 순서 고정)

A 의 확정 작업을 풀 스레드가 꺼낸 직후(DB 확정 전)에 멈춰 두었다.

| 시점 | 응답 | Redis | DB 발급 행 | 결과 API |
|---|---|---|---:|---|
| A 요청 | `ACCEPTED`(202). 요청 스레드 `Test worker` 에서 반환 | {A} | 0 | `pending` 1 |
| 멈춘 사이 A 재요청 | **`DUPLICATE`** (쿠폰이 없는데 "이미 발급") | {A} | 0 | |
| 멈춘 사이 B 요청 | **`SOLD_OUT`** | {A} | 0 | |
| 놓아준 뒤 | | {A} | 1 | `asyncResults` {SUCCESS 1}, `pending` 0 |

- 확정은 `coupon-issue-async-N` 스레드에서 실행됐고, 그 스레드에는 트랜잭션이 없었다(`isActualTransactionActive()` false). 확정 트랜잭션은 `IssueConfirmService` 가 그 스레드에서 새로 연다.
- 202 와 커밋 사이에는 Redis 예약만 있다. 3단계 4-4(보상 전 재요청)와 같은 상태가, 이번에는 정상 경로에서 매 요청마다 생긴다.

### 4-2. 접수 뒤 DB 확정 실패 (JUnit, 재고 1)

DB 확정을 커밋 직전에 실패시켰다.

| 요청 | 응답 | 확정 결과 | DB 발급 행 | Redis |
|---|---|---|---:|---|
| A | **`ACCEPTED`(202)** | `ERROR` | 0 | 비어 있음 (풀 스레드에서 보상 SREM) |
| A 재요청 | `ACCEPTED` | `SUCCESS` | 1 | {A} |

A 는 이미 202 를 받았다. 실패는 결과 API 의 `asyncResults` 에만 남고 A 에게는 전달되지 않는다. 보상이 예약을 지웠으므로 A 가 다시 요청하면 성공한다. A 가 다시 요청하지 않으면 A 는 202 를 받고도 쿠폰이 없다.

### 4-3. 큐 포화와 거부 정책 (JUnit, 스레드 4, 큐 50)

스레드 4개를 모두 DB 확정 직전에 멈추고 50건을 더 보내 큐를 채운 뒤 한 건을 더 보냈다.

| 거부 정책 | 넘친 요청의 응답 | 그 회원의 예약 | 그 뒤 |
|---|---|---|---|
| `AbortPolicy` (기본값) | **`REJECTED`, HTTP 503** (`TaskRejectedException`) | 요청 스레드가 SREM. Redis 예약 54건(넘친 회원 없음) | 놓아준 뒤 54건 모두 SUCCESS. 넘친 회원이 다시 보내면 접수되어 55건 |
| `CallerRunsPolicy` | `ACCEPTED`(202). 단 응답 전에 **요청 스레드(`Test worker`)가 DB 확정을 직접 실행**(응답까지 6~28ms), 응답 직후 이미 커밋돼 있음 | 확정됨 | 큐에 먼저 들어간 54건은 아직 멈춰 있는데 넘친 요청이 먼저 커밋. 놓아준 뒤 55건 |
| `DiscardPolicy` | **`ACCEPTED`(202), 예외 없음** | Redis 에 남음 | 풀이 모두 빈 뒤에도 확정 결과가 오지 않음(`pending` 1 그대로), Redis 에만 있는 회원 1, 그 회원 재요청 `DUPLICATE` |

- Abort 는 큐에 넣는 시점의 실패라 요청 스레드에서 바로 알 수 있다. 접수하지 않았으므로 예약을 되돌리고 503 을 돌려준다.
- CallerRuns 는 큐가 찬 동안 그 요청을 동기 방식으로 바꾼다. 요청 스레드가 확정에 묶이므로 큐가 찬 동안은 접수 속도가 확정 속도로 떨어질 것이다(배압. HTTP 로는 재지 않았다). 202 를 돌려주지만 이미 커밋된 뒤이고, 큐에서 기다리던 작업보다 먼저 커밋되어 완료 순서가 뒤바뀐다.
- Discard 는 작업을 큐에 넣는 순간 조용히 버린다. 예외도 로그도 없고, `@Async` 가 돌려준 `CompletableFuture` 는 영영 완료되지 않는다. 202 를 받은 회원은 예약만 남아 다시 요청해도 "이미 발급" 이다. 작업이 사라지는 위치가 코드 어디에도 드러나지 않는 정책이다.
- 큐가 차기 전까지 스레드는 4개를 넘지 않는다(core = max).
- 순서를 고정한 결과(4-1~4-3)는 3번 실행 모두 같았다(CallerRuns 의 응답 시간만 6~28ms 로 달랐다).

### 4-4. 동시 요청 (JUnit, 요청 50, 스레드 50, 풀 스레드 4, 큐 50)

### 4-8. 실제 프로세스 종료 (HTTP, 재고 1000, 3회씩)

[원본](results/2026-10-19-stage4-kill.md). 접수가 300건을 넘으면 앱 JVM 에 신호를 보냈다. 신호가 닿았을 때는 1000건이 모두 202 를 받은 뒤였다.

| 신호 | 신호 → 종료 | 종료 뒤 Redis 예약 | 종료 뒤 DB 발급 | 재시작 뒤 Redis 에만 있는 회원 | 그 회원 재요청 |
|---|---|---:|---:|---:|---|
| `kill -KILL` (스레드 4) | 0.16~0.2s | 1000 | 103~135 | **865~897** | 409 "이미 쿠폰 발급 받은 사용자입니다." |
| `kill -TERM` (스레드 4) | 2.75~3.7s | 1000 | 1000 | 0 | - |

- SIGKILL: 202 를 받은 1000건 중 865~897건의 확정 작업이 메모리 큐와 함께 사라졌다. 남은 것은 Redis 예약뿐이고, 그 회원들은 쿠폰이 없는데 "이미 발급" 을 받는다. 3단계 4-3(예약 뒤 종료)이 한 건이었다면, 여기서는 큐에 쌓인 만큼 한꺼번에 생긴다. 요청 기록도 메모리에 있어서, 재시작 뒤에는 누가 202 를 받았는지 앱이 모른다. Redis 와 DB 의 차이로만 알 수 있다.
- SIGTERM(스레드 4): 세 번 모두 큐에 남은 작업을 다 확정한 뒤 종료됐다. Tomcat 의 정상 종료 자체는 5ms 만에 끝났다(로그). 신호부터 프로세스 종료까지 걸린 2.75~3.7초 동안 큐에 남아 있던 확정이 처리됐다. Spring 6.2.1 의 동작을 바이트코드로 확인했다(`ExecutorConfigurationSupport`, `ExecutorLifecycleDelegate`).
  1. 컨텍스트 종료 이벤트에서 실행기에 `shutdown()`. 새 작업은 받지 않고 큐에 있던 작업은 계속 처리한다.
  2. 생명주기 정지 단계가 "실행 중인 작업 수가 0" 이 될 때까지 기다린다(Spring Boot 기본 최대 30초, `spring.lifecycle.timeout-per-shutdown-phase`).
  3. 빈 소멸 단계에서 `waitForTasksToCompleteOnShutdown=false`(기본값)이므로 `shutdownNow()`. 이때 큐에 남은 작업은 취소된다.
- 스레드 4개일 때 다 처리된 것은, 4개가 쉬지 않고 이어서 일해 실행 중 작업 수가 큐가 빈 뒤에야 0 이 됐기 때문으로 보았다. 그렇다면 스레드가 1개일 때는 작업 사이마다 0 이 되므로 큐가 버려져야 한다. 스레드 1개로 같은 실험을 3번 했다.

| 신호 (스레드 1) | 신호 → 종료 | 종료 뒤 Redis 예약 | 종료 뒤 DB 발급 | 재시작 뒤 Redis 에만 있는 회원 | 그 회원 재요청 |
|---|---|---:|---:|---:|---|
| `kill -TERM` | 0.2~0.22s | 1000 | 47~285 | **715~953** | 409 "이미 쿠폰 발급 받은 사용자입니다." |

- 예상대로 정상 종료인데도 큐에 있던 작업이 버려졌다. **정상 종료가 큐를 비워 준다는 보장은 없다.** 스레드 4개에서 다 처리된 것은 그때의 타이밍이었다.
- 2회차에는 종료 중에 처리하던 작업이 이미 닫히는 JPA `EntityManagerFactory`·Hikari 풀을 만나 `Communications link failure during rollback(). Transaction resolution unknown.` 으로 끝났고, 그 회원의 예약도 남았다(보상 SREM 이 반영되지 않음). 빈 소멸 순서상 실행기가 멈추기 전에 DB 자원이 먼저 닫힐 수 있다.
- 큐가 30초(정지 단계 기본 대기) 넘게 남아 있는 경우는 실행하지 않았다.

## 5. 보장하는 범위와 해결하지 못한 문제

| 기준 | 동기 Lua (3단계) | @Async (4단계) |
|---|---|---|
| 1인 1장, 재고 이하, 행 = `issued_count` | 지켜짐 | 지켜짐 (JUnit·HTTP 모든 회차) |
| 응답이 곧 발급 완료 | 예 (201 은 커밋 뒤) | **아니오** (202 는 큐에 넣은 뒤. 재고 1000 에서 마지막 202 때 989~992건 미완료) |
| 확정 실패를 요청한 사용자가 안다 | 예 (응답 코드) | **아니오** (결과 API 에만 남음) |
| 접수된 작업은 결국 확정 결과가 나온다 | 해당 없음 | 프로세스가 살아 있고 Abort 면 예. Discard 면 아니오(4-3). SIGKILL 이면 아니오 |
| 큐 포화 | 해당 없음 (요청 스레드가 직접 기다림) | Abort: 503 + 예약 되돌림 |
| 강제 종료 시 | 응답 전이라 클라이언트는 실패를 본다. 진행 중이던 요청의 예약만 남음(3단계 4-3) | 큐에 있던 작업이 모두 사라짐, 예약만 남음 (865~897건) |
| 정상 종료(SIGTERM) 시 | Tomcat 이 처리 중 요청을 마침 | 보장 안 됨. 스레드 4 는 3회 모두 다 처리, 스레드 1 은 715~953건 버림 |
| 먼저 온 요청이 당첨 | Redis 실행 순서 | 같음. DB 완료 순서는 더 크게 뒤섞임 |

해결하지 못한 문제
- 확정 작업 목록이 JVM 메모리에만 있다. 프로세스가 죽으면 작업이 사라지고, 무엇이 사라졌는지도 남지 않는다. Redis 와 DB 를 비교해 "예약만 있는 회원" 을 찾을 수는 있지만, 그 회원이 202 를 받았는지 응답 전에 끊겼는지는 구분할 수 없다.
- 202 를 받은 사용자는 확정 결과를 받을 방법이 없다. 실패를 보상해도(SREM) 사용자는 모른다.
- 재시작한 프로세스는 사라진 작업을 다시 실행하지 않는다.
- 접수가 몰리는 동안 확정이 거의 진행되지 않은 원인을 확정하지 못했다. 근거는 같은 기계의 CPU 경쟁을 가리킨다(4-5).

## 6. 다음 단계로 넘어가는 이유

4단계는 응답 시간을 DB 확정에서 떼어 냈다. 대신 "접수했지만 확정하지 않은 작업" 이 JVM 메모리 큐에만 있게 됐고, 프로세스가 죽으면 그 작업이 근거 없이 사라졌다(4-8).

5단계는 이 작업을 프로세스 밖(Redis Pub/Sub)으로 보낸다. 발행자와 구독자를 다른 프로세스로 나누면 발행자가 죽어도 이미 보낸 작업은 남는가? Pub/Sub 는 메시지를 저장하지 않고 그 순간 연결된 구독자에게만 전달하므로, 구독자가 없거나 끊긴 동안의 작업은 4단계와 같이 사라질 것으로 예상한다. 그 유실이 어디서 생기는지 확인한 뒤, 6단계에서 메시지를 저장하고 ACK 와 재처리를 하는 Streams 로 넘어간다.
